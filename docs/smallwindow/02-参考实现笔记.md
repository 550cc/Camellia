### 五层解析流程

```
① 锚点：唯一日志字符串字面量
     → 在数据段搜字符串（如 "Failed to load widget"）
     → 不依赖偏移、不依赖 OTA

② 反查：扫描可执行段，找 ADRP+ADD 双字窗口
     → 解码 adrp xN, page / add xN, xN, #lo12
     → 命中点即"引用该字符串的代码位置"

③ 定界：.eh_frame unwinder 求函数边界
     → [func_begin, func_end)，不需要符号表

④ 结构证明：straight(begin, end)
     → 验证替换区间内部无分支
     → 扫描整个函数体，确认没有外部跳转进入该区间
     → 防止把 trampoline 插到别人会跳进来的地方

⑤ 语义动作：Action 枚举 + Site{va, action, reg, frame, pool}
     → "打哪里 + 做什么"，而不是记录绝对地址
```

### 关键代码：operand_mask 自动掩码

```cpp
inline uint32_t operand_mask(uint32_t w);   // 按 ARM64 编码语义自动生成

inline bool pattern(const Body& b, const uint32_t* words, size_t n, uint32_t& out) {
    unsigned hits = 0; size_t selected = 0;
    for (...) {
        uint32_t mask = pooladd(...) ? 0xffc003ffu
                                     : operand_mask(words[j]);
        if ((b[i+j] & mask) != (words[j] & mask)) { ... }
    }
    if (hits != 1) return false;   // ← 唯一性硬门
}
```

**要点**：`operand_mask()` 是**按指令编码自动推导**，非手写表：
- `bl`：只比 opcode 高 6 位，跳转偏移全通配
- `add x0,x22,#imm`：比 opcode + Rn + Rd，立即数通配
- `ldur`：比 base + target reg，displacement 通配

这解释了我们的困境：**64 条精确串 ratio=2.6，但 64 条掩码串可能 ratio>10**。
因为精确匹配把"版本间必然变化的立即数"当成有效信号，
看似信息量大，实际是**噪音**，还挤掉了真正有区分度的 opcode 位。

## 二、WOMMO —— 简洁的手写掩码

### 掩码模式表示
```cpp
struct PatternWord { uint32_t value; uint32_t mask; };

{0xA9BF79FDu, kAll}         // kAll = 0xFFFFFFFF：精确匹配 stp x29,x30
{0x94000000u, 0xFC000000u}  // bl 指令：只校验 opcode 高 6 位，偏移通配
{0x00000000u, 0u}           // mask=0：完全通配（占位，跳过该 word）
```

匹配逻辑：
```cpp
for each offset i in executable range:
    ok = true
    for j in 0..n-1:
        if (mem[i+j] & mask[j]) != (value[j] & mask[j]): ok = false; break
    if ok: matches.push(i)
if (matches.size() != 1) return false;   // 同上，唯一性硬门
```

### 其它要点
- `FindUniqueWordPattern` 上限 **64 words**（够用，因为掩码质量高）
- 补丁动作：**跳到函数自身已有的 return 块**（不硬编码对象池偏移）
- 安装器幂等：重复注入不重复打补丁
- `matches != 1` → fail closed，保持原行为

## 三、NativeHookKit —— 基础设施层（最值得抄的代码）

### `src/dart_image.cpp`（8882B）

```cpp
struct Segment { uintptr_t start; size_t size; uint32_t flags; };
struct Image {
    uintptr_t bias;
    Segment segments[8];
    size_t segment_count;
    bool found;
};
```

**`AcquireImage`**：`dl_iterate_phdr` 按库名后缀匹配
```cpp
request->image->bias = (uintptr_t)info->dlpi_addr;
for each PT_LOAD phdr:
    segments[n++] = { dlpi_addr + p_vaddr, p_memsz, p_flags };
```
→ **段用「运行时地址 + memsz」表达，不是文件偏移**
→ `p_offset != p_vaddr` 完全不是问题（直接读内存）

**`RangeInExecutableSegment`**：
```cpp
address >= seg.start && address + size <= seg.start + seg.size
&& (seg.flags & (PF_R|PF_X)) == (PF_R|PF_X)
```
→ 防数据段误命中

**`FindUniqueMaskedPattern`**：
- 只扫 `PF_R|PF_X` 段
- `PatternWord{value, mask}`，`mask==0` 完全通配
- 全量线性扫描，`found != 1` 就清空返回 false

**`PatchCode`**（顺序很重要）：
```cpp
1. nhk::ProtectHookRange(address, length);   // ← 先登记保护！
2. mprotect(RWX)
3. memcpy
4. __builtin___clear_cache
5. mprotect(RX)
6. 逐 word 读回校验
```
注释原文：
> Protect first: HyperOS cleanup can `madvise(MADV_DONTNEED)` the page
> concurrently, dropping the COW page and silently reverting the patch.

**`AcquireVerifiedDartImage`**（防冒牌库）：
```cpp
snapshot = dlsym(handle, "_kDartIsolateSnapshotInstructions");
dladdr(snapshot, &info);           // 拿真实 dli_fbase
accept_path(info.dli_fname);       // 路径谓词校验，must fail closed
AcquireImageAtBase(info.dli_fbase);
```

### `include/nhk/madvise_guard.h`（788B）

注释原文：
```
XYRE memory cleanup can drop modified copy-on-write code pages and silently
revert patches. A module registers every patched range before writing; the
guard keeps those pages mapped.
```

API：
```cpp
bool EnsureMadviseGuard();                    // 首次使用时安装
bool ProtectHookRange(uintptr_t, size_t);     // 登记 [addr, addr+size)
```

### `src/madvise_guard.cpp`（14505B）机制

1. **两个后端**
   - 首选：**LSPlt GOT chain** —— 改 `madvise` 的 GOT 表项，
     多个模块可共享同一条链（因此需要 `third_party/lsplt` 打 patch）
   - fallback：**inline** —— 直接改 `madvise` 函数体
2. **GuardedMadviseWith 逻辑**
   ```
   if (advice == MADV_DONTNEED) {
      按受保护页边界切分请求：
      对非保护部分 → 转发原 madvise
      对保护部分   → 跳过（丢弃该段请求）
   } else {
      直接转发
   }
   ```
3. **身份校验**：`FindRuntimeIdentity` 通过 `/proc/self/maps` 的
   `dev:inode` 比对，确认 hook 打在我们以为的那个库上
4. 需要 `third_party/lsplt`（带 legacy scan overload patch 的 2.1.1）

## 四、四道共同铁律（三家一致）

| 铁律 | HyperCeiler | WOMMO | NativeHookKit |
|---|---|---|---|
| 唯一性命中 | `hits != 1 → false` | `matches != 1 → false` | `found != 1 → false` |
| 命中必须在可执行段 | 是 | 是 | `RangeInExecutableSegment` |
| 运行时视图 | 自解析 ELF 段 | 是 | `dl_iterate_phdr` |
| fail closed | 保留原行为 | 是 | 幂等安装器 |

## 五、我们的打包约束（来自 v18/v19 踩坑记录）

- `libhomeprobe.so` 必须以 **STORED（不压缩）** 方式打入 APK，
  否则 LSPosed `do_dlopen("base.apk!/lib/...")` 失败
- `META-INF/xposed/` 必须含：`module.prop`（含 `minApiVersion`）、
  `java_init.list`（可空）、`native_init.list`、`scope.list`
- `res/` 必须由 aapt2 生成合法 `resources.arsc`（手工拼 40B 会判无效）
- `am force-stop com.miui.home` 在此设备**无效**，必须 `killall com.miui.home`
- `pm install -r` 会改变 `/data/app/~~XXX==/` hash 路径，
  导致 LSPosed `modules_config.db` 里 `apk_path` 失效
- 签名必须 v1+v2 双签，证书与 v18 一致（CN=Probe）
- `pm install` 的 APK 必须放 `/data/local/tmp`（system_server 读不了 /sdcard）
