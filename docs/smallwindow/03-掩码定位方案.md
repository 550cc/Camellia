# 掩码定位方案（v20 核心）

> 结论先行：**256 条数据驱动掩码模板，在 49 个 8.01 系版本上实现 49/49 唯一命中、零误报，
> 且完全不依赖版本表、不依赖文件偏移假设。** 这是 v20 取代 v18 硬编码定位的基础。

## 一、实测数据集

### 样本范围
- 目录：`/sdcard/yuyu/各个版本桌面样本/`，共 57 个 APK
- **7.50 系（8 个）：不适用** —— 无 `lib/arm64-v8a/libapp.so`，只有 filament 3D 渲染库，
  说明 7.50 是旧 Java 架构，本方案（Dart AOT 指令补丁）对其无效
- **8.01 系（49 个）：全部适用**，均有 libapp.so（27.5–28.4 MB）

### 定位种子
直接复用现有探针的定位能力（`tools/smallwindow/seed.json`，从 `jni/homeprobe.c` 解析）：

| 项 | 值 |
|---|---|
| 序言锚点 `kOrig` | `fd79bfa9fd030faaef0101d1`（12 字节 = `stp x29,x30,[x15,#-16]!; mov x29,x15; sub x15,x15,#0x40`） |
| 模板长度 `TMPL_N` | 256 words (1024 字节) |
| 旧阈值 `TMPL_MIN` | 115 |

### 定位结果（49/49 pass）

```
best  = 170..201 / 256   (0.664 .. 0.785)
second=  17..19   / 256  (0.066 .. 0.074)
ratio = 9.8 .. 10.6      —— 无一例外
锚点候选数 = 1888 .. ~2000 （12 字节序言在 libapp.so 中出现 ~2000 次，绝不唯一）
```

**关键佐证**：best 的文件偏移随版本号单调递增
（`8.01.02.4349` → `0x17e44d4` … `8.01.02.9xxx` → `0x1b8f7e8`），
符合"版本迭代不断插入新函数、isValid 位置后移"的预期，说明定位结果不是巧合。

## 二、掩码的自动推导（核心方法）

### 曾以为的难点（已被推翻）
`01-方案决策.md` 第四节曾认为：
> operand_mask 的自动推导：ARM64 指令编码需要按类别判断哪些位是操作数

**实测证明不需要任何 ARM64 语义知识。** 用跨版本数据统计即可，且比语义推导更准：

### 方法
对 49 个样本，取各自 best 位置的 256 个 word，组成矩阵 `W[49][256]`：

```
vary[j]  = OR_i (W[i][j] XOR W[0][j])       // 至少变过一次的位
MASK[j]  = ~vary[j]                          // 49 个版本完全一致的位 → 必须精确
VAL[j]   = W[0][j]                           // 基准值
```

即：**保留所有版本都恒定的位，通配任何版本间变化过的位。**

### 为什么这比语义 mask 更好
- 语义 mask 要按指令类别区分 opcode / 立即数 / 寄存器，规则写错就漏或多
- 数据 mask 直接由 49 个真实样本投票得出，**没有假设可错**
- `bl <target>` 这类指令：目标地址位几乎必然变化 → 自动被通配；
  而 opcode 恒定 → 自动保留。效果与语义 mask 等价，但零规则

## 三、掩码表统计

| 指标 | 结果 |
|---|---|
| 保留位数 | **6960 / 8192 位 = 85.0%** |
| 完全精确的 word（mask=0xFFFFFFFF） | **170 / 256** |
| 完全通配的 word（mask=0） | **0** ← 关键：无信息空洞 |
| 每 word 稳定位数 | min 9 / max 32 / mean 27.2 / median 32 |

**85% 的信息保留 + 0 个全通配 word** 说明：跨版本差异是"局部、稀疏"的，
不是随机重构。这正是掩码方案成立的根本原因。

## 四、验证（fail-closed 铁律的实测）

用推导出的掩码模板（`mask_table.json`：`VAL[256]` + `MASK[256]`）重新全量扫描 49 个样本：

| 结果 | 数量 |
|---|---|
| 唯一命中且偏移 == 预期 best | **49 / 49** |
| 命中数 > 1（歧义） | **0** |
| 命中数 == 0（漏检） | **0** |
| 其余约 1965 个锚点候选被误命中 | **0** |

即 **ratio = ∞**（第二名匹配数为 0），远优于旧精确模板的 ratio 10。

### 与旧方案对比

| 方案 | 模板长度 | ratio | 需版本表 | 覆盖 |
|---|---|---|---|---|
| 旧 64 条精确 | 64 | ≈2.6 | 否 | 不可用 |
| 旧 128 条精确 | 128 | 4.3–4.9 | 否 | 风险高 |
| 旧 305 条精确 | 305 | >10 | 部分 | 需堆样本 |
| **新 256 条掩码** | **256** | **∞（second=0）** | **否** | **49/49** |

掩码方案用 85% 的信息量，换来"所有锚点候选全部排除"的确定性。

## 五、对运行时实现的要求

掩码模板解决"匹配什么"，但**在哪匹配**同样重要。设计要求：

1. **在运行时内存里扫，不在 APK 文件里扫**
   - v18 的 `EXPECT_APK_OFF = TARGET_VADDR + APK_ELF_OFF - 0x800000` 隐含 `p_offset == p_vaddr` 假设
   - 且 `APK_ELF_OFF = 0x1a1c000` 是 libapp.so 在 base.apk 内的 ZIP 偏移，**每次重装 APK 都会变**
   - 正确做法：`dl_iterate_phdr` 取 `dlpi_addr` + program headers，
     找到 `PT_LOAD && PF_X` 段 → 得到运行时 `[dlpi_addr+p_vaddr, +p_memsz)`，
     直接在该区间内搜锚点 + 掩码比对

2. **命中必须唯一且完整落在 PF_X 段内**（铁律 1、2）

3. **扫描开销**（实测参考）
   - 文件视图：28MB `bytes.find` + 1965 次 1KB 比对 = **0.04–0.06 s**
   - 运行时内存视图预计同级（memmem + 1KB 比对，段约 8MB）
   - 放在现有 100ms 重试循环内完全可接受

4. **补丁后必须 madvise guard**，否则 XYRE 清理会静默回滚（见 `01-方案决策.md` 铁律 4）

## 六、可复现步骤

```bash
cd /sdcard/projects/misharemt2/tools/smallwindow

# 1) 从 homeprobe.c 解析种子（kTmpl/kOrig/kNew/PRO_LO）
python3 parse_tmpl.py                # -> seed.json

# 2) 全量收集 49 个 8.01 样本的指纹窗口（约 3 秒）
/usr/bin/python3.9 collect_all.py    # -> dataset.json

# 3) 推导掩码 + 唯一性验证
/usr/bin/python3.9 derive_mask.py    # -> mask_table.json（含 self-check 与 49/49 验证）
```
