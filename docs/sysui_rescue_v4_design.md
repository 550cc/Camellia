# Camellia SystemUI 急救 v4

> 本文只约束 SystemUI 急救，不改变其他业务 Hook。

## 1. 为什么推倒 v2/v3

旧方案围绕 `BOOT/OK/CRASH` 和崩溃次数建立，依赖 LSPosed 注入 SystemUI 与 system_server，再以软重启、摘 Hook、清缓存等动作单调加码。它有三个根本问题：

1. SystemUI 已黑屏时，进程内的 BOOT/OK 可能根本不存在；观察者自身若被 LSPosed 安全模式停掉，也不能承担最终救援。
2. “进程崩了”不是根因。APK 更新、模块替换和 Hook 异常需要完全不同的恢复手术。
3. 杀进程无法撤销 `/data/app` 更新或模块挂载；清缓存/清数据不解决这三类根因，反而可能伤害用户数据。

v4 的最终兜底是 **root 独立守护**。Java 侧只做附加取证，不参与最终决策，也不主动修改 LSPosed 配置。

## 2. 三类根因与手术

### A. 安装了损坏的 SystemUI 更新

判定：包管理器显示 `codePath` 在 `/data/`，且本次故障前快照记录到来源/APK 变化。

手术：备份故障 APK 与包信息后，仅执行：

```sh
pm uninstall-system-updates com.android.systemui
```

这撤销该应用的更新并回到分区版本，**不等于 `pm clear`**。之后等待包管理器恢复、SystemUI 启动并做健康复查。

### B. root 模块挂载/替换了 SystemUI

判定：从启用的 `/data/adb/modules` 或待生效的 `/data/adb/modules_update` 模块树中发现 SystemUI 文件，快照显示该集合或内容发生变化，并有 SystemUI 故障证据。

手术：仅对 **单一、可定位** 的候选模块创建 `disable` 文件，记录模块名，然后请求重启。`modules_update` 中导致下次启动失败的候选标记 `remove`，不触碰其他模块。

只杀 SystemUI 不会撤销 systemless 挂载，因此这里必须重启。模块 ID、原始文件清单和操作结果写入历史；若模块内容动态变化，不承诺恢复用户修改，只禁用该模块。

### C. LSPosed Hook 异常

LSPosed 自带安全模式是主救援通道。v4 不再自动设置 `persist.camellia.sysui.hookoff`，不自动改 scope，不与安全模式叠加“治疗”。

- 观察到安全模式已生效：只记录并等待。
- 无法证明 Hook 是根因：不因崩溃堆栈偶然出现模块名就禁用模块。
- 用户明确选择“关闭 Camellia 对 SystemUI 的 Hook”时，才执行手动动作；这属于用户决策，不是自动归因。

## 3. 独立健康探测

守护每 5 秒采样，组合以下证据：

1. `pidof com.android.systemui`；
2. `dumpsys activity services` 中存在 `.SystemUIService`；
3. `dumpsys window windows` 中存在 `StatusBar` 或 `NotificationShade` 窗口。`NavigationBar` 只作为附加信息：手势导航等合法状态下它可以不存在，不能据此判死。

**进程存在不等于界面健康。** 必须连续多次失败才判为失活，默认持续 45 秒；开机和包变更后另有宽限期。息屏、开机早期、守护自身恢复动作期间不动手术。恢复后要求连续多次健康才结案。

另有崩溃环兜底：短时间内多次进程更换，且始终没有形成稳定健康窗口，也进入故障流程。正常的一次重启不会触发。

## 4. 变更台账与归因

状态目录：`/data/adb/camellia_rescue/`。

快照包含：

- `pm path` / `dumpsys package` 得到的 SystemUI 来源；
- 实际 APK 路径、大小和 SHA-256；
- 含 SystemUI 文件的启用 root 模块 ID 与对应文件摘要；
- 上次稳定健康状态、近期崩溃证据、恢复历史。

只有“**故障 + 已观察到的来源变更 + 唯一候选**”才自动执行 A/B 手术。第一次启动守护时没有旧快照，不凭空猜测历史根因。无法唯一归因时只做保守软重启一次；仍失败则熔断并保留现场，不批量禁用模块、不撤销所有系统更新。

每条恢复记录包含 before/after、原因、候选、动作、健康复查结果。日志不包含 LSPosed 数据库、账号、Cookie 或其他应用数据。

## 5. 动作顺序与熔断

1. 保存日志、包信息、来源快照和候选清单。
2. 有明确 A/B 证据：只执行对应手术一次。
3. 无明确证据：只软重启 SystemUI 一次，不修改包和模块。
4. 手术失败或健康未恢复：进入熔断，不循环杀进程，不继续升级动作。
5. 用户通过物理旁路或设置页明确确认后，才可针对候选执行手动恢复或解除熔断。

默认同一开机最多一次自动手术；24 小时最多两次。禁止 `pm clear`，禁止自动回滚其他系统应用，禁止自动禁用 LSPosed 或全部 root 模块。

## 6. 物理紧急旁路

黑屏时不能依赖 Compose 设置页。守护监听实体音量键：

- 黑屏/失活期间，10 秒内按 **音量上 3 次**，只请求一次“保守软重启”；
- 若存在唯一 APK/挂载候选，再按 **音量下 3 次**，表示用户明确确认针对该候选恢复；
- 每次触发有震动反馈（可用时），操作和结果写入历史；
- 没有候选时音量下不会扩大动作，不会变成“禁用全部模块”。

按键只在故障窗口或手动 `arm` 窗口生效，避免与日常调音量冲突。它调用与自动流程相同的安全检查和熔断，不是绕过一切限制的隐藏开关。

## 7. 手动入口

脚本提供：

- `status`：健康、来源、候选、熔断、最近动作；
- `restart`：软重启 SystemUI；
- `recover-update`：确认存在 `/data` 更新后撤销；
- `disable-mount <模块ID>`：仅禁用指定模块；
- `arm [秒]`：打开物理旁路窗口；
- `fuse-reset`：解除熔断；
- `export`：导出急救日志；
- `selftest`：固定夹具 + DRYRUN，不操作系统。

设置页只显示真实状态与这些明确动作，不再宣称尚未部署的分级救援。

## 8. Java 侧边界

`SysUiRescue.java` 保留单一 `attachBaseContext` 锚点和一个默认未捕获异常处理器，只写异常日志与尽力而为的 Settings 镜像。它不安装启动时序锚点，不发送 BOOT/OK，不据此判断健康，也不杀进程、清数据、撤包或改模块。异常记录器会调用 SystemUI 原有下游 handler，保留 `LogBufferEulogizer` 等系统取证链。恢复完全由独立守护决定，因此取证开关不控制恢复。

`SysUiWatch.java` 仅保留 system_server 崩溃取证，不输出救援 verdict、不触发动作。若 LSPosed 安全模式停用它，root 守护仍能独立工作。

## 9. 验证

必须先做：shell 语法、固定夹具、DRYRUN、状态机与锁测试。

真机故障注入分别验证：无害测试更新、专用测试挂载模块、LSPosed 安全模式。每次注入前先确认可回退项；未获用户明确同意，不在正常设备上自动制造黑屏、撤销更新、禁用模块或重启。
