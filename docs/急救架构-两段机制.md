# camd 急救架构 v4：两段机制（启动救护 / 运行期修复）

> 状态：**A 段已落地**（`phase_de`/`mod_scan`/`disable_module`/`hard_reboot`/`write_pending`/`a_phase`，
> 见 §7.5）；B 段（装包/快照/交接单）仍为设计。
> 关键前提：SystemUI 崩 → 锁屏画不出来 → 解不了锁 → CE 永不解密 → `pm` 永不可用。
> 因此 **A 段是唯一能让用户"重新操作手机"的窗口；A 失败则 B 永不可达**。

---

## 1. 为什么必须分两段

| | **A：启动救护** | **B：运行期修复** |
|---|---|---|
| 时间窗 | boot 开始 → 锁屏可用（CE 未解密） | CE 可用 → 关机 |
| 目标（单一） | **让 SystemUI 起来，用户能看到锁屏** | **装回用户想要的状态，清脏数据，防复发** |
| 可用手段 | 禁模块、删包、软/硬重启（全部免 `pm` 免 UI） | 以上 + `pm install`、`pm uninstall-system-updates`、`pm clear` |
| 不可用 | **`pm` 全部不可用**、CE 数据不可读 | —— |
| 结束条件 | SystemUI 稳定 → 等解锁；CE 可用 → 交接给 B | 关机 |

**A 求"活"，B 求"好"。** A 只做能不依赖任何 Android 服务的事。

---

## 2. 共用：故障源判定器（A/B 同一份）

按"从外到内"剥离，顺序固定：

| 序 | 故障源 | 判据 | 为什么排这个位置 |
|---|---|---|---|
| 1 | **挂载模块** | `/proc/self/mountinfo` 显示 `/system/priv-app/SystemUI*` 或 plugin 路径被 `/data/adb/modules/*` 覆盖；且该模块无 `disable` 标志 | 挂载层在最上，**不先剥它，删 `/data/app` 的包无效** |
| 2 | **本体覆盖包** | `find_ovl("com.android.systemui")` 命中 | 装了更新包 |
| 3 | **界面组件** | `find_ovl(<plugin>)` 命中，或 plugin 存在而 SystemUI 崩 | 有 fallback，风险最低 |

判定前提：先确认 SystemUI **真的在崩**（pid 采样），否则不做任何动作。

## 3. 机制 A：启动救护

### 3.1 时序

```
service.d 拉起 camd (up≈38)
   ↓
等 system_server：PMS 起来后才有 pid（实测 up≈41–44）
   ↓
pid 采样窗口 W=120s：变化 ≥3 次 → 崩溃循环
   ↓
判定故障源（第 2 节）→ 按类型处置
   ↓
SystemUI 稳定存活 ≥ stable_sec(60s) → A 段完成，等用户解锁
   ↓
检测 CE 可用（`getprop sys.user.0.ce_available` 为 `true`）→ 写交接单 → B 段接管
```

### 3.2 先取证，再按代价从低到高用药

**核心原则：对症才用药，用药先用便宜的药。硬重启不是默认手段。**

| 手段 | 代价 | 副作用 |
|---|---|---|
| 软重启 `killall system_server` | 低（15–25s） | camd 不受影响，状态不丢，可反复 |
| 硬重启 `reboot` | 高（40–60s） | 全系统重来；盲目使用会形成重启循环 |

**取证（两项都在 DE 可读，已实测）**

| 证据 | 来源 | 含义 |
|---|---|---|
| **E1 装错包** | `packages.xml` → `<package name="X" codePath="/data/app/…">` | 该包有 `/data/app` 覆盖版本 |
| **E2 模块挂载** | `/proc/self/mountinfo` → 目标路径被 `/data/adb/modules/*` 覆盖，且无 `disable` 标志 | 文件被模块层替换 |

`packages.xml` 用现成的 `abx_scan` ABX 解析器（`tools/abx_scan.c`，361 行，结构化取 name+codePath，无猜测），内联进 camd 即可。

**处置矩阵**

| 证据 | 首选手法 | 为什么 |
|---|---|---|
| **E1**（有覆盖包，无模块） | 删包 + **软重启** | PMS 重扫 `/data/app` 发现 codePath 缺失 → 自动回退系统分区版。**软重启就够，不需要硬重启** |
| **E2**（有模块挂载，无覆盖包） | 禁模块 + **硬重启** | Magisk 在 post-fs-data 建立 overlay，zygote 继承该 mount ns；`killall system_server` 后新 system_server 仍继承 → **挂载不消失，必须整机重启重走 post-fs-data** |
| **E1+E2**（两者都有） | 先删包 + 软重启 | 先用便宜的对症药；仍崩再禁模块 + 硬重启 |
| **都无** | 软重启 1 次 | 无对症证据时硬重启也无用（没东西可禁可删），**不乱动手**，只留证 |

**结论：硬重启只在「确认存在模块挂载」时使用。** 其余全部走软重启——这正是你说的：装错包用 xml 判出来，软重启就能救。

### 3.3 S2 分支：system_server 也起不来（真砖）

```
读 /data/adb/camellia/boot_state：上次 boot 是否完成过
  连续 2 次未完成 → 本次在 system_server 启动前直接：
     禁用所有影响 SystemUI 的模块 + 删其覆盖包
     → 硬重启
```

这是唯一能在"ADB 都连不上"时自救的路径。

### 3.4 交接单（A → B）

CE 可用瞬间写 `/data/adb/camellia/handover.json`：

```json
{"boot_id":123,"a_actions":["disable_module:xxx","rm_ovl:com.android.systemui"],
 "pending_install":"miui.systemui.plugin","bad_sha256":["ab12..."]}
```

`pending_install` = A 段想装但没权限装的（用户指定的组件包）。B 起来第一件事就是补装。

## 4. 机制 B：运行期修复

### 4.1 组件修复链（**回答你的问题：指定包优先于卸载更新**）

```
① 装用户指定 apk（component_apk）      ← 最优先
   ↓ 装后验活 stable_sec，崩了 → 该 sha256 打入 bad 名单，永不再试
② 装最近健康快照（snap）
   ↓ 验活
③ 卸载更新 pm uninstall-system-updates  → 回退系统原版
   ↓ 验活
④ 删包 + 软重启                          ← 通用兜底
```

**为什么指定包 > 卸载更新：**

1. 卸载更新 = 回到**系统原版**，这只是"中立默认值"，不代表用户想要——他很可能就是因为原版有问题才装新版的。
2. 指定包 = 用户**明确认可的目标状态**，语义等级更高。
3. 先卸更新再装指定包，等于同一个包动两次，中间多一个"原版运行窗口"，还多消耗一次崩溃/重启预算。

**但必须配坏包标记**：指定包本身可能是个坏 apk，装上去继续崩。所以装后观察期一崩就记 sha256，不再重试，直接降到 ③。这是防止无限循环的关键。

### 4.2 指定包合法性校验（你要求的）

安装前必须解出 apk 内 `AndroidManifest.xml` 的 `package` 属性，与配置的 `component_pkg` 严格比对：

```
不符 → 拒绝安装 → 记 APK_PKG_MISMATCH → 直接跳到 ④ 兜底（删包+软重启）
```

不能只比文件名/路径，那是不可靠的。技术路线见第 7 节。

### 4.3 其他故障源在 B 段

| 故障源 | B 段补充动作 |
|---|---|
| 挂载模块 | 同上（禁模块 + 硬重启），另可提示用户模块名 |
| 本体覆盖包 | `pm uninstall-system-updates com.android.systemui`（比删目录更干净）+ 软重启 |
| 组件 | 4.1 四段链 |
| 脏数据 | `pm clear <pkg>`（仅 B 段可用） |

## 5. 备份 / 快照的定位（各司其职）

| | 目录 | 时机 | 内容 | 用途 |
|---|---|---|---|---|
| **坏包留证** | `bad/` | 删包前 | 只移 `base.apk` + `.meta`（pkg/vc/sha256/lastUpdateTime/原因） | 留证；**不复制整个目录**（省空间）；误判可恢复 |
| **健康快照** | `snap/` | 运行 ≥ `stable_sec` 且零崩 | 只存 `base.apk` + `.meta` | 作为 B 段 ② 的装回源 |

> **已落地**（A 段部分）：`bak_save()` 原本 `cp -a` 整个覆盖目录，现改为
> **只存 `base.apk` + `meta`**（`pkg`/`ovl`/`sha256`/`ts`/`reason`），目录仍沿用
> `bak_dir`（不改名以免破坏既有配置与轮转逻辑）。`bak_prune` 的 `<pkg>@<uptime>`
> 轮转语义不变。
>
> 两处策略刻意不同：
> - **A 段（`a_phase`）**：归档失败 **不阻塞** 删包 —— 黑屏急救，救活开机优先；
> - **B 段（`fix_pkg`）**：归档失败 **放弃** 删包 —— 运行期从容修复，保守优先。
>
> `sha256` 拿不到（个别机型 toybox 无 `sha256sum`）时记 `unknown`，不写假值；
> 它是后续坏包黑名单的唯一可靠键。
>
> 尚未落地：`snap/`（健康快照）与 `bad/`（坏包黑名单匹配）。

## 6. 预算与熔断

| 项 | 单 boot 上限 |
|---|---|
| 软重启 | 2 |
| 硬重启 | **≤1，且仅在确认存在模块挂载时** |
| 删包 | 2 |
| 装包（B） | 2 |

- 同一故障源**连续 3 次 boot** 都失败 → 熔断，只保开机，不再自动动作
- 任何一级失败立即记 `ABORT`，**不重试同级**（重试是无效循环的主要来源）
- 硬重启前必须先落盘计数（`sync`），否则重启丢状态 → 无限重启

## 7.5 实现记录与踩坑（A 段）

### 7.5.1 模块检测：mountinfo 方案作废，改纯文件系统扫描

原设计用 `/proc/self/mountinfo` 找 `/data/adb/modules/*` 的 overlay。
**实测不成立**：设备上 23 个模块，但 camd 自己 `grep /data/adb` 得 0 条。

原因：KernelSU/Magisk 的模块挂载落在**各 app 进程自己的 mount namespace** 里
（zygote fork 后由模块注入），camd 从 init 起来处在**全局 namespace**，
看不到别人 namespace 的挂载。所以 camd 视角下 mountinfo 永远「干净」。

改为三条纯文件系统判据（不依赖 mount 表，任何 namespace 结论都一致）：

| 判据 | 检查点 | 含义 |
|---|---|---|
| **S1 priv-app 布局** | 模块目录下存在 `system/priv-app/MiuiSystemUI/` | 模块在替换 SystemUI 本体 |
| **S2 根级 apk** | `system/` 或模块根目录直接有 `*.apk` | 模块往 system 塞 apk |
| **S3 脚本内容** | `service.sh`/`post-fs-data.sh`/`action.sh`/`log.sh` 内含 `SystemUI`/`priv-app`/`overlay` 等关键字 | 模块用脚本动态挂载 |

`mod_scan(ids, max, include_disabled)` 返回**活跃**（无 `disable` 标志）的模块 id 列表；
`mod_is_systemui(dir)` 做单模块判定。实测能准确识别 `systemui_mount`。

### 7.5.2 踩坑一：一条会形成**无限重启循环**的分支（已删除）

早期实现里有个兜底分支：

```c
/* 有模块但全部已 disable → 认为「只差重启生效」→ 重启 */
if (nmod == 0 && mod_scan(ids, 16, 1) > 0 && st_get(key) == 0)
    hard_reboot();
```

**这是错的，且致命**：设备上 `systemui_mount` **本来就长期带 `disable`**，
该条件每次开机进 DE 都成立 → 每次都硬重启；而硬重启会**更换 `boot_id`**，
「同一 boot 只救一次」的幂等标记随之失效 → 新 boot 又成立 → **永久卡在重启循环**。

正确的模型：模块已 `disable` 表示它本就不生效，**重启不改变任何事实**，
所以该分支改为只记一条节流日志，然后继续走正常归因路径，不再抢占 return。

> 教训：**任何「发现自己改的东西已是目标状态 → 于是再动一次」的分支都要警惕**，
> 尤其在幂等键会被自己动作重置的场合（重启换 boot_id 是最典型的自毁幂等）。

### 7.5.3 踩坑二：dry-run 保护必须集中，不能逐分支判断

A 段所有副作用（写 pending、写 state、禁模块、`rm -rf`、软/硬重启）原本各分支各自
`if (dry) return;`，结果上面那条兜底分支**漏写**，在「自以为只在打印」的测试里
真的执行了 `reboot`。

现改为**单一闸门** `g_a_dry`，由 `--a-phase` 默认置位；所有副作用点统一走它。
另外 `--a-phase --apply` 在 CE 阶段（已解锁）直接 `REFUSE` —— 用户正常用机时
绝不允许删包/重启。

静态复核结论：`a_phase` 通往硬重启只剩 1 条路径、通往软重启只剩 1 条路径，
均在 `g_a_dry` 守卫之后。

### 7.5.4 状态如何让用户看见

A 段动作全发生在开机过程中（用户往往整段都不知道），且
`/data/system/camellia_action/*.pending` App 无权限读。因此：

- camd 把动作摘要写进 state（`a_last_action` / `a_last_pkg` / `a_last_why` / `a_last_ts`）
- `ui_dump()` 每 5s 广播 `camd_status.txt`，新增字段：
  `phase=DE|CE`、`a_mod=<活跃模块数>`、`a_last_action`、`a_last_pkg`、`a_last_why`、`a_last_ts`
- Java 侧 `CamdRescue.phaseDe()/aModCount()/aLastSummary()` 读取，
  设置页摘要显示「上次急救: delete_apk com.android.systemui」

`a_mod` 需遍历模块目录 + 读脚本，不能跟 5s 节流，故在 `ui_dump` 内做 **60s 缓存**。

## 10. B 段修复链（已实现）

B 段的动作不再是「一上来就删覆盖层」，而是按代价从轻到重依次尝试，
任一步成功即停：

| 步骤 | 手段 | 代价 | 失败后 |
|---|---|---|---|
| ① | `pm uninstall-system-updates <pkg>` | 退回出厂版本，用户数据不动 | 静默进 ② |
| ② | `pm install -r -d <user_apk>` | 覆盖为预先备好的好包 | 静默进 ③ |
| ③ | 删覆盖层 + 软重启 | 物理移除注入源，最重 | 记 FAIL，进熔断计数 |

为什么顺序不能倒：②③ 都会让 system_server 连带 camd 一起重启，
一旦先做了，更轻的手段就再没机会被试到。

**入口**

- 自动：`rescue_tick()` 判定目标包 pid 变化后调用 `ui_rescue_chain()`
- 手动：
  - `camd --set-apk <x.apk>` — 设置 / 查看 / 清空兜底包（设置时立即解析包名校验）
  - `camd --install-apk <x.apk> [期望包名] [--dry]`
  - `camd --uninstall-update <包名> [--dry]` — 注意 `--dry` 写在包名**之后**

**安全边界**

- `user_apk` 只开给命令行，不开给 UI 文件通道（`ui_apply()` 白名单拒绝）。
  否则任何能写通道文件的 App 就等于拿到「让 camd 以 root 装任意包」的能力。
- 装包前强制 `apk_pkgname()` 解析并与期望包名比对，不符即拒 —— 装错包会二次搞坏系统。
- 装后校验不复信 `pm` 的自述（见下节）。

## 11. 踩坑：packages.xml 是 ABX 二进制，且没有 version / lastUpdateTime

**现象**：`--install-apk` 灰度测试报「装后状态未变 vc=0」，但 `pm` 明明返回 Success。

**排查**

1. `grep 'name="com.example.myapp"' /data/system/packages.xml` —— 一条都匹配不到。
2. `strings` 只捞到 `name`、`codePath`、`databaseVersion`、`sdkVersion` 等少数词。
3. 结论：Android 12+ 的 `packages.xml` 是 **ABX（Android Binary XML）**，不是文本 XML；
   且新版本里 `<package>` 元素**只保留 name / codePath 等少数属性**，
   `versionCode`、`lastUpdateTime` 属性根本不存在。

**后果**：`pkg_query()` 里这两个字段恒为 0，拿它们做「装后是否变化」的判据，
会让每一次安装都被误判成失败。

**修法**

- `pkg_query()` 保留（ABX 解析器是对的，`codePath` / `name` 能正常读到）。
- 新判据 `apk_stamp()`：`stat(codePath/base.apk)` 的 `mtime` 与 `size` 组合值。
  重装必然重写 base.apk，mtime/size 必然变化。
- 判定规则：`codePath` 变了 → 成功；`codePath` 相同但 stamp 变了 → 成功；
  两者都没变才判「装后未变」。

**验证**：连续两次 `--install-apk` 同一个文件，codePath 的 hash 目录每次都变
（`~~J3dNk31Ybyg4j...` → `~~BMUBGxDq4IDE...`），说明判据有效。

**另一处噪音**：`pm uninstall-system-updates` 对普通应用 / 不存在的包会抛
`java.lang.NullPointerException`（pm 自己在 `ApplicationInfo` 上解引用空指针）。
camd 侧把它归纳成「X 不是系统更新应用（无可卸更新）」，不把堆栈透给用户。
