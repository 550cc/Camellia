# 实弹记录 2026-11-03：SystemUI 覆盖层坏包崩溃循环救援

> 环境：Xiaomi 2509FPN0BC / Android 17 (API 37) / LSPosed 模块 Camellia
> 二进制：camd v2.29.2（versionCode 119），运行时 md5 `0adf00a3fe61f550`
> 日志归档：`docs/logs/rescue-20261103.log`、`docs/logs/camd-20261103.log`
> 结论：**救援成功，但判定迟钝（211 s / 8 次崩溃）**，根因已定位，修复方案见 §6

---

## 1. 测试意图

此前从未在真机上验证过「SystemUI 自己有 `/data/app` 覆盖层且崩溃」这条路径。
历史唯一一次 A 段触发（`up=10551`）走的是保护分支：

```
[up=10551] A_TRIGGER sysui crashloop circ=3 thr=3 win=180s
[up=10551] A_NO_OVL pkg=com.android.systemui (ROM builtin, refuse to delete)
```

即 SystemUI 无覆盖层 → camd 主动拒绝删除。本次补上这条空白路径。

## 4. 根因：归因被插件化堆栈污染，且「不可行动」不会降级

MIUI 的 SystemUI 是插件化架构（`miui.systemui.plugin`），崩溃堆栈里带 plugin 的帧，
于是 `culprit_attr()` 把这次 SystemUI 崩溃归到了 **plugin** 包上。
而 plugin 当时没有 `/data/app` 覆盖层（真正坏的是 SystemUI 的覆盖层）。

`tools/camellia_rescue.c` 定性分支（约 2905~2930 行）：

```c
if (attr == ATTR_PLUGIN && !isp) continue;
any_cand = 1;
if (!find_ovl(pkgs[i], d, sizeof(d))) continue;   /* 归因包无覆盖层 → continue */
matched = 1;
...
if (!matched)
    rlog(any_cand
         ? "TICK_NO_OVL attr=%s (目标包无 /data/app 覆盖层，无可删物)"
         : "TICK_NO_MATCH attr=%s (配置 target 里无对应包，本轮不动)", ...);
```

问题：归因命中的包 **没有可删物** 时，代码只是 `continue` 然后整轮放弃，
**不会 fallback 到另一个「有覆盖层」的候选**。于是明明 SystemUI 有覆盖层且在崩溃循环，
判定却被 plugin 的「无可删物」卡住，连续 5 个 tick（249/279/309/339/369）空转。

最终救回来靠的是退化判据 `only-sysui-overlay(lu=0)`：等旧 dropbox 条目滑出 60 s 窗口、
归因落空后，才按「只有 sysui 有覆盖层」认定。**这是运气，不是设计**——
若配置里再多一个有覆盖层的包，这条退化判据也会失效。

## 5. 救援动作本身是正确的

| 环节 | 表现 |

| 快照 | `BAK_SAVE /data/adb/camellia/bak/com.android.systemui@399 src=… sha=9af08c49…` ✅ `meta` 224 B 完整（`pkg` / `ovl` / `sha256` / `ts` / `reason=delete_bad_package`），历史遗留的 `meta missing` 本次未复现 |
| 删除 | `FIX_DONE pkg=com.android.systemui removed=/data/app/~~XzUTs…` ✅ |
| 计数复位 | `A_HIST_RESET` / `CRASH_HIST_RESET` ✅ |
| 软重启 | `SOFT_REBOOT cmd=[killall system_server] sr_count=1` ✅ 实测生效 |
| 回落 | 覆盖层消失，`pm path` 回到 `/system_ext/priv-app/MiuiSystemUI/MiuiSystemUI.apk`，`versionCode=202602260` ✅ |
| 熔断余量 | `sr_count=1`，远未触及 `soft_reboot_limit(2/2)` ✅ |

即：**删包 + 软重启 + 回落 ROM 版** 这条核心链路在 SystemUI 本体上首次实弹验证通过。
问题纯粹在「什么时候动手」，不在「动手做对没做对」。

## 6. 待办修复：归因包不可行动 → fallback 到可行动候选

改动范围仅限上述定性分支：

1. `attr` 明确（PLUGIN / SYSUI）但该类包 `find_ovl()` 失败时，**不再整轮放弃**
2. 扫描全部候选，收集「有覆盖层」的包集合
   - 恰好 1 个 → 立即修它，日志标记归因已降级：`TICK_ATTR_INVALID attr=plugin -> fallback pkg=<x>`
   - ≥2 个 → 走已有的双修路径（`TICK_ACT both`，处理完统一软重启一次）
3. 原则不变：能定性的仍只动被认定的那个包；只有「归因包不可行动」才降级

**预期效果**：本场景从 `211 s / 8 次崩溃` 降到 `约 60 s / 3 次崩溃`（一级计数达标即刻动手）。

**复测素材现成**：`/data/adb/camellia/bak/com.android.systemui@399/base.apk` 即本次有效的坏包。
