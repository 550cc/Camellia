# HyperOS 系统急救（自愈）机制分析

> 分析对象：Xiaomi 2509FPN0BC / HyperOS `OS4.0.0.23.XPBCNXM` / Android 17 (API 37)
> 分析方法：`/system_ext/framework/miui-services.jar` 反汇编 + 设备实机验证
> 分析日期：见文件修改时间

---

## 0. 一句话结论

系统里有**一整套「崩溃监护 → 分级救援」的自动流程**：某个关键包反复崩溃时，系统会**自己动手**——先清它的配置、再清设置、再热重启、再清数据、最后恢复出厂。这套流程在你的机器上**已经真实触发过**（SystemUI 被重置过 DeviceConfig）。

所以：**你手机里某些设置/功能会「莫名其妙自己变回去」，很可能就是它干的。**

---

## 1. 它解决什么问题

传统的 Android 遇到「关键进程无限崩溃」只能卡在开机动画（bootloop）。Google 的方案叫 **RescueParty**：同一组件在短时间内崩够次数，就按等级逐步「拆掉可能出问题的东西」，保命优先。

小米在这个基础上做了 **RescuePartyPlus**（名字里的 Plus），把处理粒度做得更细，并且覆盖了**桌面、SystemUI、字体、主题、云控配置**这些 MIUI 特有部件。

```
  进程反复崩溃
       │
       ▼
┌──────────────────────────┐
│ PackageWatchdog（看门狗） │  记录「谁失败了、失败了几次」
└───────────┬──────────────┘
            │ 达到阈值
            ▼
┌──────────────────────────┐
│ RescueParty / Plus（救援）│  按等级选择「拆什么」
└───────────┬──────────────┘
            │
   ┌────────┼─────────┬──────────────┬─────────────┐
   ▼        ▼         ▼              ▼             ▼
 清配置   清设置    热重启        重置主题字体    清数据/恢复出厂
```

## 2. 代码架构（三层）

| 层 | 类 | 所在 dex | 职责 |
|---|---|---|---|
| AOSP 底座 | `com.android.server.PackageWatchdog` | services.jar | 监测包的持续失败，把失败历史持久化到 `package-watchdog.xml` |
| **小米扩展** | `com.android.server.PackageWatchdogImpl` | **miui-services.jar** | 继承 `PackageWatchdogStub`，覆写救援步骤，实现 8 级救援 |
| 执行动作库 | `com.android.server.RescuePartyPlusHelper` | miui-services.jar | 具体动作：清缓存/清数据、重置主题字体、禁用自启、云控回滚、APEX 重置 |
| 启动期初始化 | `com.android.server.SystemServerStub` / `SystemServerImpl` | miui-services.jar | 启动时读写 `sys.rescueparty.home.level`、`sys.rescueparty.systemui.level` |
| 数据上报 | `miui.mqsas.sdk.event.GeneralExceptionEvent`（type = `0x1AE` = 430） | miui-services.jar | 每次救援上报到 MQSAS 稳定性平台 |

> **坑点**：`SystemServerStub.initAppRescuepartyLevel(Context)` 在 services.jar 里是**空方法**（只有 `return-void`）。真实逻辑在 `SystemServerImpl` 里，别被空壳骗了。

### 关键调用链（从崩溃到救援）

```
App/系统进程 crash
  └─> PackageWatchdog.notifyPackageFailure(versionedPackage, reason)
        └─> PackageWatchdogImpl.doRescuePartyPlusStepNew(mitigationCount, package, ctx)
              ├─ RescuePartyPlusHelper.checkDisableRescuePartyPlus()   // 总开关检查
              ├─ RescuePartyPlusHelper.setMitigationTempCount(count)   // 记录计数
              ├─ isPersistentSystemApp() / SYSTEM_PROCESS_MONITOR_LIST // 只救「系统级」包
              ├─ RescuePartyPlusHelper.checkPackageIsCore()            // 核心包直接跳过
              ├─ checkRescueMonitorPackages()                          // 记录 + 上报
              └─ switch (mitigationCount) { ... 分级动作 ... }
```

## 3. 两套救援等级（重点，容易混淆）

系统里同时存在**两套枚举**，数字含义完全不同：

### 3.1 AOSP 侧（`crashrecovery-events.txt` 里写的就是这套）

| 值 | 名称 | 动作 |
|---|---|---|
| 1 | `SCOPED_DEVICE_CONFIG_RESET` | 重置**部分** DeviceConfig（按命名空间） |
| 2 | `ALL_DEVICE_CONFIG_RESET` | 重置**全部** DeviceConfig |
| 3 | `WARM_REBOOT` | 软重启（只重启 framework，不动内核） |
| 4 | `RESET_SETTINGS_UNTRUSTED_DEFAULTS` | 重置「不可信」的设置项为默认值 |
| 5 | `RESET_SETTINGS_UNTRUSTED_CHANGES` | 重置「不可信」的设置改动 |
| 6 | `RESET_SETTINGS_TRUSTED_DEFAULTS` | 重置「可信」设置项为默认值 |
| 7 | `FACTORY_RESET` | 恢复出厂设置 |

### 3.2 小米 RescuePartyPlus（`RescuePartyPlusHelper` 的 `RESCUE_LEVEL_*`）

| 值 | 常量名 | 备注 |
|---|---|---|
| 0 | `RESCUE_LEVEL_NONE` | 什么都不做，仅清理消息队列 |
| 1 | `SCOPED_DEVICE_CONFIG_RESET` | 同 AOSP |
| 2 | `ALL_DEVICE_CONFIG_RESET` | 同 AOSP |
| 3 | `WARM_REBOOT` | 热重启 |
| 4 | `RESET_SETTINGS_UNTRUSTED_DEFAULTS` | |
| 5 | `RESET_SETTINGS_UNTRUSTED_CHANGES` | |
| 6 | `RESET_SETTINGS_TRUSTED_DEFAULTS` | |
| 7 | `FACTORY_RESET` | 最高级 |

### 3.3 小米还有一套「缓解等级」（`PackageWatchdogImpl` 里的 `LEVEL_*`）

| 值 | 名称 |
|---|---|
| 0 | `NONE` |
| 1 | `RESET_SETTINGS_UNTRUSTED_DEFAULTS` |
| 2 | `UNTRUSTED_CHANGES` |
| 3 | `TRUSTED_DEFAULTS` |
| 4 | `WARM_REBOOT` |
| 5 | `FACTORY_RESET` |

> ⚠️ 注意这三套枚举**编号不对应**。看日志时必须先确认是哪个体系的数字。

## 5. 关键实现解读（smali → 伪代码）

### 5.1 总开关 `checkDisableRescuePartyPlus()`

```java
static boolean checkDisableRescuePartyPlus() {
    if (SystemProperties.getBoolean("persist.sys.rescuepartyplus.disable", false)) {
        Slog.w("RescuePartyPlus", "RescueParty Plus is disable!");
        return true;   // 已禁用，救援流程直接退出
    }
    if (SystemProperties.getBoolean("persist.sys.rescuepartyplus.enable", false)) {
        Slog.w("RescuePartyPlus", "This device support and enable RescuePartyPlus! (Via cloud control)");
    }
    return false;      // 默认（未 disable）= 允许救援
}
```

**要点**：默认是**开启**的，只有显式 `disable=1` 才关。`enable` 那行只是打日志，不改变返回值。

### 5.2 救援主体 `doRescuePartyPlusStepNew(int mitigationCount, VersionedPackage pkg, Context ctx)`

伪代码（按 smali 分支还原）：

```java
if (checkDisableRescuePartyPlus()) return false;          // 总开关
setMitigationTempCount(mitigationCount);

if (pkg == null || pkg.getPackageName() == null) goto 收尾;

// 只救「常驻系统应用」或「系统进程监控名单」里的包
if (!isPersistentSystemApp(ctx, pkg) && !SYSTEM_PROCESS_MONITOR_LIST.contains(pkg))
    goto 收尾;

String cur = pkg.getPackageName();
if (RescuePartyPlusHelper.checkPackageIsCore(cur)) {       // 核心包不救
    Slog.e(TAG, "Skip because system crash: " + pkg);
    return false;
}

checkRescueMonitorPackages(cur, mitigationCount, ctx);     // 计数 + 上报

GeneralExceptionEvent event = new GeneralExceptionEvent();
event.setType(0x1AE);                                      // 430
event.setPackageName(cur);
event.setSummary("rescueparty level: " + mitigationCount);

switch (mitigationCount) {
  case 7:  // FACTORY_RESET
      removeMessage(6, cur);
      clearAppCacheAndData(ctx, pm, cur);                  // 清数据
      details = cur + " RESCUE_LEVEL_FACTORY_RESET;CLEAR_APP_CACHE_AND_DATA;";
      if (cur.equals(getLauncherPackageName(ctx))) goto send;   // 桌面：到此为止
      if (RescuePartyPlusHelper.checkPackageIsTOPUI(cur)) {
          resetTheme(cur);                                 // 重置主题
          SystemProperties.set("sys.attempting_reboot", "true");
          setLastResetConfigStatus(true);
          executeWarmReboot(ctx);                          // 热重启
          return true;
      } else {
          disableAppRestart(cur);                          // 禁用自启
          details += "DISABLE_APP_RESTART;";
      }
      break;

  case 6:  // RESET_SETTINGS_TRUSTED_DEFAULTS
      removeMessage(5, cur);
      details = cur + " RESCUE_LEVEL_RESET_SETTINGS_TRUSTED_DEFAULTS;";
      if (checkPackageIsTOPUI(cur)) {
          pm.deleteApplicationCacheFiles(cur, null);        // 清缓存
          resetFont(cur);                                   // 重置字体
          cloudDataRollBackAPP(cur, ctx);                   // 云控数据回滚（广播）
          for (String plugin : SYSTEMUI_DEPEND_APPS)
              pm.deletePackage(plugin, null, 2);            // 卸载 SystemUI 插件
      }
      break;

  case 0:  // NONE
      removeMessage(7, cur);
      details = cur + " RESCUE_LEVEL_NONE;";
      if (cur.equals(getLauncherPackageName(ctx))) goto 收尾;
      break;

  // case 1..5 同构：先 removeMessage，再按 TOP_UI / 普通应用分派动作
}

sendMessage(cur, level, event);   // 投递给上报/执行线程
```

### 5.3 `disableAppRestart(String pkg)`

```java
static void disableAppRestart(String packageName) {
    if (TextUtils.isEmpty(packageName)) {
        Slog.e("RescuePartyPlus", "Disable app auto restart failed, because package is empty");
        return;
    }
    SystemProperties.set("sys.rescuepartyplus.disable_autorestart." + packageName, "1");
    PackageManagerServiceUtils.logCriticalInfo(3,
        "Finished rescue level DISABLE_APP for package " + packageName);
}
```

`logCriticalInfo` 会落到 `/data/system/` 的事件文件，也就是 `crashrecovery-events.txt` 一类记录。

### 5.7 它会不会「重装系统应用」？——不会

**结论：整套救援链路里没有任何安装/重装动作。**

证据（对 `RescuePartyImpl`、`RescuePartyXM`、`RescuePartyPlusHelper`、`PackageWatchdogImpl` 四个类逐一审计）：

| 检查项 | 结果 |
|---|---|
| 方法名含 `install` | 0 命中 |
| 方法名含 `uninstall` | 0 命中 |
| 方法名含 `reinstall` | 0 命中 |
| 字节码调用 `installExistingPackageAsUser` | 0 命中 |
| `miui-services.jar` 全库 `\breinstall` | 仅 2 处，均为 Preinstall 预装服务字符串 |
| 唯一 `PackageManager` 写操作 | `deletePackage()` ×4，另有 `deleteApplicationCacheFiles` / `clearApplicationUserData` |

那 4 处 `deletePackage` 的对象是 `SYSTEMUI_DEPEND_APPS` 集合里的成员，日志固定为 `"Try to rollback Top UI App plugin: xxx"`。

**所以「回滚」是靠卸载插件实现的**：SystemUI / 桌面加载的是 MIUI 插件包，卸载后自动回落到系统内置基线，不需要重新安装。

真正会动应用包或数据的只有三种：

1. `PackageManager.deleteApplicationCacheFiles()` —— 清缓存
2. `PackageManager.clearApplicationUserData()` —— 清数据
3. `PackageManager.deletePackage()` —— 卸载 SystemUI 依赖插件（4 处，模式一致）

> 如果真的需要「重装系统应用」（例如 `pm install-existing com.miui.home`），那是 `PackageManagerService.installExistingPackageAsUser` 的职责，属于 PackageManager 体系，**救援链路从未调用它**。

## 7. 这套机制能被拿来做什么（Camellia 模块视角）

Camellia 是 LSPosed 模块，作用域包含 `system_server`（`android` 包）。这意味着：**在 system_server 进程内可以直接反射拿到 `PackageWatchdogImpl` 实例**，也有权限读 `/data/system`、`/mnt/rescue`。所以下面的功能都可行。

### ① 模块自保 / bootloop 守卫 ⭐ 最推荐

**问题**：模块 hook 把 system_server 搞崩 → 无限重启 → 用户只能进 recovery。

**做法**：
1. 每次启动早期读 `sys.rescueparty.systemui.level`、`/data/system/crashrecovery-events.txt`、`boot_count`
2. 若发现「上次启动后等级上升」或「boot_count 在短时间内连续 +1」
3. 自动把 Camellia 的 hook 全部降级（写 prefs `safe_mode=true`），本次只加载设置 UI，不加载 hook

**实现要点**：读取要放在 `HookEntry` **最早期**，且读失败时必须「不启用安全模式」（fail-open），避免误判把自己永久关掉。
**风险**：低。只读 + 写自己的 pref。

### ② 系统健康面板 ⭐ 推荐

在设置页加一屏，只读展示：

- 当前救援等级（home / systemui）
- `package-watchdog.xml` 里的 mitigation-count
- 最近 10 条 `crashrecovery-events.txt`
- `/mnt/rescue/mqsas/stabilityrecord/` 里的 ANR / 内核 / OCP 记录摘要
- tombstone 数量
- 被 `disable_autorestart` 标记的包

**价值**：手机出问题时不用连电脑抓 bugreport。
**风险**：零（纯读）。

### ③ 一键开关 RescuePartyPlus

```java
SystemProperties.set("persist.sys.rescuepartyplus.disable", "1");   // 关
SystemProperties.set("persist.sys.rescuepartyplus.disable", "0");   // 开
```

**适用场景**：你不想让系统自动清你的 DeviceConfig / 主题 / 字体。
**风险**：中。关掉后真出 bootloop 就少了自救能力（AOSP 基础 RescueParty 仍在）。

### ④ 救援前自动备份 DeviceConfig / 主题字体

hook `RescuePartyPlusHelper.resetTheme` / `resetFont` / `clearAppCacheAndData` / `resetApexData`，在真正动手前把相关内容快照到 `/sdcard/Camellia/rescue-backup/<时间戳>/`，事后可一键还原。

**价值**：直接解决「SystemUI 被重置 → 设置全丢」的问题（本机已发生 2 次）。
**风险**：中低。备份写 sdcard，注意别备份过大的缓存目录。

### ⑤ 阻止指定包自动重启

```java
SystemProperties.set("sys.rescuepartyplus.disable_autorestart." + pkg, "1");
```

**适用场景**：某个应用反复崩、不想它疯狂自启耗电。
**风险**：中。对系统关键包使用可能导致桌面空白，必须限制白名单。

### ⑥ 崩溃根因归因工具

解析 `stabilityrecord/HangChart.txt`、`LocalHangRecord.txt`，在模块里展示「最近 30 天谁崩了、崩在哪、什么类型（ANR / native / 内核 / OCP）」。

**价值**：比翻 bugreport 快得多，也能看出是不是模块导致。
**风险**：零。

### ⑦（不建议）主动触发热重启

```java
// 内部方法，需反射调用
executeWarmReboot(context);
```
**风险**：高。误触 = 用户正在用的 App 全被杀，且可能进入救援流程。

### 不建议做的事（红线）

| 行为 | 后果 |
|---|---|
| 主动把 `mitigation-count` 改大 | 直接触发清数据 / 恢复出厂 |
| 伪造 `sys.attempting_reboot=true` 不重启 | 系统状态机卡死，可能真的 bootloop |
| 对 `com.miui.home` 写 `disable_autorestart` | 桌面起不来，只有状态栏 |
| 删除 `/mnt/rescue/mqsas/` 下文件 | 破坏容灾记录，出问题无法回溯 |
| 长期 `disable=1` 后又装不稳定模块 | 失去最后一道自救网 |

# 11. Magisk / KernelSU 模块改装 SystemUI：救援机制为什么救不回来

> 本章全部结论来自 `miui-services.jar` / `services.jar` 反编译实证 + 本机 root 实测，不含推测。

## 11.1 本机现状核查

| 项目 | 实测结果 |
|---|---|
| Magisk 本体 | `/data/adb/magisk/magisk` **不存在**，`magisk -v` 无输出 |
| 实际框架 | KernelSU 系（存在 `zygisksu`、`mountify`、`lunarkernelmodule`、`wb2api`、`hanamaki_kernel`） |
| `/data/adb/modules` | 23 个模块目录 |
| **SystemUI 覆盖模块** | **`systemui_mount`** → `system/system_ext/priv-app/MiuiSystemUI/MiuiSystemUI.apk`，当前 `disable=Y` |
| `disable` 标记机制 | `/data/adb/modules/<id>/disable` 存在即不挂载；**Magisk / KernelSU / APatch 通用** |

结论：用户的改装方式是「模块 overlay 覆盖 `system_ext/priv-app/MiuiSystemUI/MiuiSystemUI.apk`」，走的是**挂载命名空间 overlay**，不是修改真实分区。

## 11.2 SystemUI 在 MIUI 救援体系里的特殊地位（源码实证）

三个关键集合的真实内容：

| 集合 | 所在类 | 内容 | 作用 |
|---|---|---|---|
| `APP_WHITE_LIST` | `com.android.server.RescuePartyXM$1`（HashSet） | **`{ com.android.systemui }`（唯一元素）** | 命中即**豁免恢复出厂** |
| `CORE_PACKAGE` | `RescuePartyPlusHelper$2` | `{ "android" }` | 命中则 `Skip because system crash`，整条救援链直接放弃 |
| `TOP_UI_PACKAGE` | `RescuePartyPlusHelper$4` | `{ com.android.systemui }` | 命中则走「清缓存 / 重置主题 / 重置字体」专用分支 |

`com.android.systemui` 的处境：

- ✅ 是持久化系统应用 → 通过 `isPersistentSystemApp()` 前置过滤，**会进入救援流程**
- ✅ 不在 `CORE_PACKAGE` → **不会被 Skip**，会被真的执行救援动作
- ✅ 在 `TOP_UI_PACKAGE` → 走 TOP UI 专用分支
- ✅ 在 `APP_WHITE_LIST` → **level 7 恢复出厂被豁免**

即：SystemUI **会被反复「救治」，但永远不会被「重装/恢复出厂」修复**。

## 11.3 完整失效链（`com.android.systemui` 视角）

### 第一层：`RescuePartyXM.executeRescueLevelInternal`（等级 → 动作）

```java
switch (level) {
  case 1: break;                                        // 无动作
  case 2: if (isFlagResetEnabled() && failedPackage == null)
              executeDeviceConfigReset(); break;        // 仅 pkg== 时重置 DeviceConfig
  case 3: executeWarmReboot(ctx, level, pkg); break;    // 软重启（system_server 重启）
  case 4: break;                                        // 无动作
  case 5: break;                                        // 无动作
  case 6: break;                                        // 无动作
  case 7:
      if (APP_WHITE_LIST.contains(pkg) && pkg != null) return;   // ← SystemUI 在此 return
      if (isRebootPropertySet()) return;
      executeFactoryReset(ctx, level, pkg);             // 只有 pkg== 或非白名单才走到这
}
```

- `executeWarmReboot` 有节流：`shouldThrottleReboot()` + `DEFAULT_FACTORY_RESET_THROTTLE_DURATION_MIN = 0x5a0 = 1440 分钟`
- `getMaxRescueLevel()` 受 `persist.device_config.configuration.disable_rescue_party_factory_reset` 压制
- 全局开关：`persist.sys.enable_rescue`、`persist.device_config.configuration.disable_rescue_party`、`persist.sys.disable_rescue`、USB 连接状态、eng 版本（`isDisabled()`）

### 第二层：`PackageWatchdogImpl.doRescuePartyPlusStepNew(count, pkg, ctx)`

前置门禁：

```java
if (RescuePartyPlusHelper.checkDisableRescuePartyPlus()) return false;
setMitigationTempCount(count);
if (pkg == null || pkg.getPackageName() == null) goto 跳过;
if (!isPersistentSystemApp(ctx, pkg) && !SYSTEM_PROCESS_MONITOR_LIST.contains(pkg)) goto 跳过;
if (checkPackageIsCore(pkg)) { Slog.e("Skip because system crash"); return false; }
if (checkPackageIsTopUI(pkg)) { ... }   // SystemUI 命中
```

分等级动作（SystemUI 命中 TOP_UI）：

| count | SystemUI 实际动作 |
|---|---|
| 6 | `deleteApplicationCacheFiles("com.android.systemui")`<br>`resetFont()`、`cloudDataRollBackAPP()`<br>**遍历 `SYSTEMUI_DEPEND_APPS = {miui.systemui.plugin, com.miui.aod}` 逐个 `deletePackage(plugin, null, 2)`** |
| 7 | `clearAppCacheAndData("com.android.systemui")`<br>`resetTheme("com.android.systemui")`<br>`SystemProperties.set("sys.attempting_reboot", "true")`<br>`setLastResetConfigStatus(true)`<br>**`executeWarmReboot(ctx)`** → return true |
| 7（非 TOP UI 应用） | `disableAppRestart(pkg)` → 写 `sys.rescuepartyplus.disable_autorestart.<pkg>=1`，再清数据 |

`disableAppRestart` 的唯一调用者就是 `doRescuePartyPlusStep` / `doRescuePartyPlusStepNew`；读取侧是 `ActivityManagerServiceImpl.checkAppDisableStatus(pkg)`（读同一 prop，命中打印 `Disable App [pkg] auto start!`）。

### 第三层：为什么对「挂载改装」完全无效

| 救援动作 | 作用位置 | 对 Magisk/KernelSU overlay 的效果 |
|---|---|---|
| 清缓存 `deleteApplicationCacheFiles` | `/data/data/<pkg>/cache` | 无效——故障源在 `/system_ext` overlay |
| 清数据 `clearApplicationUserData` | `/data/data/<pkg>` | 无效，且会丢 SystemUI 配置 |
| 重置主题 `resetTheme` | `/data/system/theme*` | 无效 |
| 重置字体 `resetFont` | `/data/system/fonts` | 无效 |
| 云数据回滚 `cloudDataRollBackAPP` | `/data/mqsas/...` | 无效 |
| 卸载 UI 插件 `deletePackage(miui.systemui.plugin)` | `/data/app` | 仅能修「插件导致」的崩溃，**修不了主 APK 被覆盖** |
| 恢复出厂 `executeFactoryReset` | 重建 `/data` | **对 SystemUI 被 `APP_WHITE_LIST` 豁免，永不执行** |
| 重装系统应用 | —— | **不存在该动作**（全 jar `reinstall*` 仅 2 处，属 `BackgroundPreinstalloptService`，与救援无关） |

**救援体系的全部设计前提是「故障来自 `/data` 里的可变状态」**，因此它只清 `/data`。而 overlay 位于挂载命名空间，救援进程根本感知不到，也没有任何 API 可以卸载模块。

## 11.4 结果：软砖死循环，而不是数据被毁

> ⚠️ **本节结论已被第 12 章实测修正。**
> 「无限热重启」是纯代码推导的预期；本机实测中 RescueParty 等级恒为 0、`RescuePartyLog` 为空，救援链一级都未触发。
> 实际故障路径是 `versionCode 降级 → PMS 拒绝更新 → bootmonitor hyperboot timeout`，请以 **12.3 / 12.4** 为准。

```
改装版 SystemUI 崩溃
   → PackageWatchdog mitigationCount++（跨重启持久累加）
   → count 到 6：清 SystemUI 缓存 + 卸载 UI 插件（无效，重启又装回）
   → count 到 7：清数据 + 重置主题 + warm reboot（无效，模块仍挂载）
   → SystemUI 重新启动 → 仍是被覆盖的改装版 → 再崩
   → 循环
```

关键坏消息：

1. **永远不会升级到「更彻底」的手段**——最彻底的 `executeFactoryReset` 被 `APP_WHITE_LIST` 挡住。
2. **没有任何动作会触碰 `/data/adb/modules`**——模块始终生效。
3. `sys.rescuepartyplus.disable_autorestart.<pkg>` 会禁止 SystemUI 自动重启 → 表现为**黑屏无界面**（连崩溃对话框都没有），此时更难自救。
4. Session/数据不会丢，但**用户无法进入任何界面**，等价于软砖。

好消息（可逆性）：

- `disable_autorestart` 与等级 flag 都是 `sys.*` / `Settings.Global` 层面，**改文件系统就能恢复**
- 模块 overlay 不写真实分区，**删/禁用模块目录即可 100% 复原**

## 11.5 唯一的真正自救途径（都是人工）

| 途径 | 操作 |
|---|---|
| Recovery / 侧载 shell | `rm /data/adb/modules/systemui_mount/disable` 的反向：`touch /data/adb/modules/systemui_mount/disable` |
| 已开启的 adb | `adb shell su -c 'touch /data/adb/modules/systemui_mount/disable'` |
| 安全模式 | 部分 KernelSU 版本在安全模式下不加载模块 |
| 文件管理器（MT管理器等，root） | 直接在 `/data/adb/modules/<id>/` 建空文件 `disable` |

注意：**必须在开机前生效**。因为 overlay 在 `post-fs-data` 阶段挂载，模块一旦进入挂载命名空间，本次开机内无法撤销（要重启）。

## 11.6 Camellia 可落地的防护功能设计

### 方案 A：崩溃熔断 + 自动禁用覆盖模块（推荐，救人于砖）

- Hook 点：`PackageWatchdogImpl.doRescuePartyPlusStepNew`（已在 `android` scope 内，可直接 hook）
- 逻辑：
  1. 命中 `pkg == "com.android.systemui"` 且 `count >= 3`（可配）
  2. 扫描 `/data/adb/modules/*/`，检测 `system*/**/MiuiSystemUI*` 覆盖项，且该模块**无** `disable` / `remove` 标记
  3. 通过 `su -c "touch /data/adb/modules/<id>/disable"` 写入熔断标记
  4. 写 Camellia 日志 + 在 `/sdcard/Camellia/rescue/` 留一份说明
  5. 可选：直接触发 `reboot`（否则用户仍黑屏）
- 依赖：root（system_server uid 1000 无 `/data/adb/modules` 写权限，必须 `su`）
- 收益：把「软砖 + 人工救」变成「自动回退到原版 SystemUI」

### 方案 B：装机前静态体检（无 root 依赖，纯提示）

- 设置页新增「SystemUI 改装体检」：
  - 遍历 `/data/adb/modules/*/`（该目录本机为可读），列出所有覆盖 `MiuiSystemUI` / `SystemUI` 的模块及启用状态
  - 读 `/system/system_ext/priv-app/MiuiSystemUI/MiuiSystemUI.apk` 的 `versionCode` / 签名，与 `/data/system/packages.xml` 里已安装的 `com.android.systemui` 对照
  - 不一致 → 醒目警告：「你正在运行被模块覆盖的 SystemUI，MIUI 救援机制无法自救，且恢复出厂被白名单豁免」
- 收益：把风险前置暴露

### 方案 C：救援旁观者日志（诊断/取证）

- Hook `RescuePartyXM.executeRescueLevel` + `PackageWatchdogImpl.setCrashApplicationLevel`
- 记录 `(pkg, level, count, 时间, 触发的动作)` 到 `/data/system/camellia_rescue.log`
- 收益：黑屏后重启可回看「它到底做了什么、为什么没救回来」，也便于判断是否要禁用模块

### 方案 D：拦截 warm reboot 死循环（激进）

- Hook `PackageWatchdogImpl.executeWarmReboot`，若判定「崩溃源是 overlay 且模块未禁用」→ 改为写 disable 标记而不重启
- 风险：若崩溃其实是真故障，跳过重启会延长不可用时间。建议仅在方案 A 同时生效时启用

**推荐组合：B（前置警告）+ A（自动熔断）+ C（诊断日志）。**

## 11.7 一句话结论

> ⚠️ 本节为第 11 章的**代码推导结论**，其「无限软重启」部分已被第 12 章实测推翻。
> 保留原文用于对照「预期 vs 实测」的差异，最终结论请读 **12.9**。

> 救援机制不是「重装系统应用」的机制，而是「清 `/data` 里可能坏掉的状态」的机制。
> Magisk/KernelSU 模块改装 SystemUI 的故障源在 `/system` 的 overlay 层，**救援机制在原理上就够不到**；而唯一能彻底修复的 `executeFactoryReset` 又恰好把 `com.android.systemui` 放进了豁免白名单。
> 所以：**有真实的「恢复不过来」风险，表现为无限软重启 + 黑屏软砖，数据不丢但界面全无。**
> 唯一可靠解法不是靠系统救援，而是**在崩溃达到阈值时由第三方（Camellia）主动写 `/data/adb/modules/<id>/disable` 熔断模块**——这正是方案 A。

# 12. versionCode 降级陷阱与急救机制的结构性盲区

> 本章是实测补充章节，**修正第 11.3 / 11.4 节的预期**。
> 第 11 章基于代码推导，认为「SystemUI 被 overlay 改坏 → 崩溃计数升高 → 反复清数据 + 热重启 → 无限软重启软砖」。
> 实测结果是另一条更隐蔽的路径：**救援机制全程未参与，故障以 bootmonitor 启动超时的形式呈现，且系统自认为一切正常。**

## 12.1 事故形态：版本号差一亿的静默降级

`MiuiSystemUI` 是三份 apk 在设备上共存的：

| 来源 | 大小（字节） | versionName | **versionCode** |
|---|---|---|---|
| PMS 记录值 / 模块改装版 `sysui_mod.apk` | 52,400,312 | 17.03.260226.r | **102602260** |
| 当前磁盘 `/system_ext/priv-app/MiuiSystemUI/MiuiSystemUI.apk` | 52,019,850 | 17.03.260226.r | **202602260** |
| 用户准备的「原版」`sysui_system.apk` | 52,019,850 | 17.03.260226.r | **202602260** |

两个关键事实：

1. **`versionName` 三者完全相同**（`17.03.260226.r`）。任何通过「设置 → 应用信息」或 `pm list packages` 观测的手段都看不出差异。
2. **`versionCode` 相差 100,000,000（一亿）**。这是「把日期编码进 versionCode」与「模块作者手工抬高 / 覆盖」两种编码约定碰撞的结果：
   - `202602260` = 2026-02-26 版（MIUI 日期式编码）
   - `102602260` = 在 `02602260` 前加 `1`

改装版把 versionCode 抬高一亿，是模块作者为了让 overlay 版**能覆盖**系统版而故意做的（否则同 versionCode 会被 PMS 忽略）。这个手法能让覆盖生效，但同时制造了**不可回退**。

## 12.2 PMS 僵局（`dumpsys` 实证）

```
codePath=/system_ext/priv-app/MiuiSystemUI
versionCode=102602260            ← PMS 认定「已安装」的版本
versionName=17.03.260226.r
flags=[ SYSTEM HAS_CODE PERSISTENT ALLOW_BACKUP ]
timeStamp=2009-01-01 08:00:00
lastUpdateTime=2026-08-25 09:48:38   ← 从 8 月至今纹丝未动
firstInstallTime=1970-01-01 09:35:05
```

而磁盘上那个 apk 的 versionCode 是 **202602260**。

```
PMS 记录：102602260
磁盘文件：202602260      ← 降级
lastUpdateTime 停在 2026-08-25  ← PMS 拒绝用低版本覆盖自己的记录
```

辅助证据：

| 路径 | 时间 | 说明 |
|---|---|---|
| `/data/system/package_cache/3c6e.../MiuiSystemUI-16-1683617712` | 2026-08-25 09:09 | PMS 解析缓存，自 8 月起未重建 |
| `/data/dalvik-cache/arm64/system_ext@priv-app@MiuiSystemUI@...` | 2026-10-17 02:47 | dexopt 产物，与当前磁盘 apk 不一定匹配 |

**这是 Android 层面的硬规则**：`PMS` 在扫描时若发现「磁盘版本 < 已记录版本」，判定为 downgrade 并拒绝更新记录。对系统分区包，它既不能卸载也不能替换，于是选择**保持旧记录、按旧记录工作**——不报错、不告警、不写 critical log。系统进入「记录与实际不一致」的静默矛盾态。

## 12.3 急救机制的真实反应（与第 11 章预期的重大差异）

| 观测项 | 实测值 | 说明 |
|---|---|---|
| `sys.rescueparty.systemui.level` | **0** | 救援等级从未升高 |
| `sys.rescueparty.home.level` | 0 | 同上 |
| `getprop` 中 `sys.set_app_crash_level.flag` | **不存在** | 崩溃等级机制从未启用 |
| `sys.rescuepartyplus.disable_autorestart.*` | **不存在** | 救援链未走到「禁用重启」 |
| `/mnt/rescue/mqsas/RescuePartyLog/` | **空目录** | AOSP 式 `RescuePartyXM` 从未写入日志 |
| `sys.mqs.recorder.rescueparty.finish` | `true` | 仅表示 mqs 记录器打包完成 |
| `/mnt/rescue/mqsas/UnhealthyBootLog/bm_hyperboot_timeout_901005303_popsicle_OS4.0.0.23.XPBCNXM_5953118.zip` | **12,288,751 字节 / 2026-10-18 14:44** | **bootmonitor 判定启动超时** |
| 同目录 `kmsg.txt` / `pmsg.txt` / `uefi.txt` | 10-18 14:44 | 启动失败现场快照 |

**结论：第 11 章预期的「清缓存 → 清数据 → 热重启 → 无限软重启」链条，在这台机器上一级都没有触发。**

真实发生的是：

```
overlay 改装版被禁用 / 磁盘被换成低版本 apk
        ↓
PMS 拒绝降级记录，保持 versionCode=102602260
        ↓
SystemUI（PERSISTENT + coreApp）与 PMS 状态不一致，反复启动失败
        ↓
它不产生 java crash，PackageWatchdog 收不到崩溃事件
        ↓
表现为「开机卡在启动阶段」
        ↓
bootmonitor 触发 hyperboot timeout，打包 kmsg/pmsg/uefi 到 /mnt/rescue/mqsas/UnhealthyBootLog/
        ↓
系统放行继续启动 → 界面空白 / 无状态栏
```

即：**从「应用崩溃救援」路径，切换到了「启动超时取证」路径。后者只收集现场信息，不做任何修复。**

## 12.4 五处冲突

### 冲突一：判据错位 —— 急救机制只认「崩溃次数」，降级不产生崩溃

- `PackageWatchdogImpl` / `RescuePartyPlusHelper` 的升级链全部基于**崩溃/ANR 计数**。
- SystemUI 是 `PERSISTENT` + `coreApp`，被 system_server 强拉；启动失败会表现为**启动阶段卡死**，而不是 java 层 crash 或 ANR。
- 因此看门狗**永远收不到事件**，等级恒为 0。
- 后果：急救机制既没机会「越救越坏」，也**完全没机会做任何事**。它是被绕过的，不是被触发的。

### 冲突二：能力错位 —— bootmonitor 只取证，不识别包状态

- bootmonitor 判定超时后的唯一动作是：打包 `kmsg/pmsg/uefi` → 放行。
- 它**没有**任何逻辑去读 `packages.xml`、比对 versionCode、校验 dalvik-cache。
- 而 PMS 把这个降级矛盾视为「正常状态」（静默拒绝更新）。
- **后果：系统所有自愈路径共享同一个盲区——「降级不匹配」是它们眼中的合法状态。** 这是「删了模块也救不回来」的最深层原因：系统不认为自己坏了。

### 冲突三：双重豁免 —— SystemUI 注定享受不到终极修复通道

- `RescuePartyXM.APP_WHITE_LIST = { com.android.systemui }`（唯一元素）→ **level 7 恢复出厂对它豁免**。
- 同时它**不在** `CORE_PACKAGE = { "android" }`（不会被 Skip）。
- 后果：即便等级真的升到 7，系统也会跳过它，继续在无解状态里运行。若它是普通 App，早就被恢复出厂清掉了。

### 冲突四：时序错位 —— overlay 与 bootmonitor 观察窗口不重叠

- bootmonitor 判定超时发生在开机 early 阶段，此时 KernelSU/mountify 的 overlay 刚挂好或仍在挂载。
- 打包出的 kmsg 中，SystemUI 的 dex/资源加载记录与最终 overlay 内容**未必一致**。
- 后果：现场信息不可靠，无法用于定位。这也解释了模块作者为何要另写 `action.sh` 救砖，而不指望系统救援——他知道系统救不了。

### 冲突五：双入口互斥 —— `action.sh` 与系统救援抢同一位置（**已修正**）

> **⚠ 修正说明**：本节早期版本称「`action.sh` 往 `/system_ext` 物理层塞 apk」。经 2026 年本轮源码与实机双重核查，该论断**错误**，现更正如下。

- `action.sh` 的目标是 `AIM_APK="${MODDIR}/system_ext/priv-app/MiuiSystemUI/MiuiSystemUI.apk"`，
  设备上 `$MODDIR/system_ext` 是指向 `./system/system_ext` 的**符号链接**。
  → 它写的是 **overlay 源文件**，**不是** `/system_ext` 物理分区。
- 实机反证：`/system_ext/priv-app/MiuiSystemUI/MiuiSystemUI.apk` 的 mtime 为 `2009-01-01 08:00`
  （只读分区烧录时间戳），**说明该文件自出厂从未被替换过**。
- 更强的反证：模块 `config/settings.conf` 中 `PROTECT_COUNT=0`
  → 救砖逻辑**一次都没有成功执行过**，不存在「塞入低版本」的行为。
- 真正的不一致来源是：模块 **overlay 生效期间**（2026-08-25 09:07 安装，09:48 触发 PMS 扫描），
  PMS 扫描到 overlay 中的 102602260 改装版并写入 `packages.xml`；
  2026-09-04 05:26 用户创建 `disable` 标记禁用模块后，overlay 消失，
  但 PMS **不重新扫描**（`codePath` 未变），于是留下「记录 102602260 / 磁盘 202602260」的**陈旧元数据**。
- **结论修正**：该不一致属于**元数据陈旧**，Android 以 `packages.xml` 为准并不重读 apk，
  因此它**本身不导致黑屏、也不阻止 SystemUI 启动**。
  本轮实测：模块 `disable` 存在、无任何 overlay 挂载、磁盘 apk 为 202602260，
  而 `com.android.systemui` 仍正常运行（`pidof` 有值）。

## 12.5 `action.sh` 的三处缺陷（把救砖变成降级炸弹）

模块 `action.sh` 的救砖段落，其核心是：

```bash
AIM_APK="${MODDIR}/MiuiSystemUI.apk"     # 模块根目录
TARGET_DIR="/system_ext/priv-app/MiuiSystemUI"
cp -af "${AIM_APK}" "${TARGET_DIR}/"     # 无条件覆盖
chown root:root "${TARGET_DIR}/MiuiSystemUI.apk"
chmod 644 ...
restorecon -RF "${TARGET_DIR}"
```

缺陷一：**路径根本不对，常态下是空转**

`ls "${MODDIR}/MiuiSystemUI.apk"` → `No such file or directory`。
文件实际只在 `system/system_ext/priv-app/MiuiSystemUI/MiuiSystemUI.apk`。
所以这段代码平时什么也不做；哪天有人按它的期望往模块根目录放一个 apk，它才会真正行动——**而行动时不做任何校验**。

缺陷二：**完全不做 versionCode 比较**

脚本的权限、属主、SELinux 上下文处理得一丝不苟（`chown` / `chmod 644` / `restorecon -RF`），全部正确。
但 PMS 的降级检查是**权限之外的另一道闸门**：即便文件系统层面完美，只要「磁盘 versionCode < 已记录 versionCode」，PMS 就拒绝。
结果：**一个「权限全对、SELinux 全对、系统丝滑地进入永久黑屏」的救援动作。** 这比权限错误更危险——因为它看起来完全成功。

缺陷三：**没有回滚，也没有校验生效**

脚本 `cp` 完就结束了。它不验证：
- 复制后的 apk 能否被 `aapt` 解析（是否是被破坏的重打包产物）
- versionCode 是否 ≥ PMS 记录值
- `restorecon` 后是否真的能挂载（SELinux 允许）
- PMS 是否接受了新包（`dumpsys package | grep versionCode` 是否变化）

**所谓「救砖」，在这个实现下等于：从「能跑」变成「永久黑屏且禁用模块无效」。**

### 参考：带 versionCode 闸门的正确写法

```bash
#!/system/bin/sh
# 安全救砖：源 apk 的 versionCode 必须 >= 已安装版本，否则拒绝
MODDIR=${0%/*}
SRC="${MODDIR}/MiuiSystemUI.apk"
DST_DIR="/system_ext/priv-app/MiuiSystemUI"
DST="${DST_DIR}/MiuiSystemUI.apk"
PKG="com.android.systemui"

log() { echo "[rescue] $*" > /dev/null 2>&1; }

[ -f "$SRC" ] || { echo "ERROR: 缺少源 apk: $SRC"; exit 1; }

# 取 versionCode：优先 aapt，回退 dumpsys（读的是 PMS 记录）
vc_of_file() {
  aapt2 dump badging "$1" 2>/dev/null | sed -n 's/.*versionCode=.\([0-9]*\).*/\1/p' | head -1
}
VC_SRC=$(vc_of_file "$SRC")
# PMS 记录值 = 当前"已安装"版本，是降级判定的基准
VC_INSTALLED=$(dumpsys package "$PKG" 2>/dev/null | sed -n 's/.*versionCode=\([0-9]*\).*/\1/p' | head -1)

[ -n "$VC_SRC" ]       || { echo "ERROR: 无法读取源 apk versionCode"; exit 1; }
[ -n "$VC_INSTALLED" ] || { echo "ERROR: 无法读取已安装 versionCode"; exit 1; }

echo "源 versionCode=$VC_SRC  已安装=$VC_INSTALLED"
if [ "$VC_SRC" -lt "$VC_INSTALLED" ]; then
  echo "REFUSED: 源 apk 版本低于已安装版本，覆盖将触发 PMS 降级拒绝并导致界面无法启动"
  echo "请改用 versionCode >= $VC_INSTALLED 的 apk，或先降级 PMS 记录（不推荐）"
  exit 2
fi

cp -af "$SRC" "$DST" || exit 1
chown root:root "$DST"
chmod 644 "$DST"
restorecon -RF "$DST_DIR"

# 校验生效
sleep 1
VC_NOW=$(dumpsys package "$PKG" 2>/dev/null | sed -n 's/.*versionCode=\([0-9]*\).*/\1/p' | head -1)
if [ "$VC_NOW" != "$VC_SRC" ]; then
  echo "WARN: PMS 记录的版本仍为 $VC_NOW（期望 $VC_SRC），本次覆盖未生效"
  echo "      可能需要在 recovery 中清 /data/system/package_cache 与 dalvik-cache"
else
  echo "OK: 已生效 versionCode=$VC_NOW，请重启"
fi
```

## 12.6 恢复路径（按可靠性排序）

### 档 1：找回 versionCode = 102602260 的原厂 apk（最干净）

覆盖回 `/system_ext/priv-app/MiuiSystemUI/MiuiSystemUI.apk`，让磁盘与 PMS 记录一致：

```bash
su
mount -o rw,remount /system_ext 2>/dev/null   # 部分机型需在 recovery/overlay 下操作
cp -af /path/to/original_102602260.apk /system_ext/priv-app/MiuiSystemUI/MiuiSystemUI.apk
chown root:root /system_ext/priv-app/MiuiSystemUI/MiuiSystemUI.apk
chmod 644 /system_ext/priv-app/MiuiSystemUI/MiuiSystemUI.apk
restorecon -RF /system_ext/priv-app/MiuiSystemUI
reboot
```

判定是否成功：

```bash
dumpsys package com.android.systemui | grep versionCode
# 期望与 ls -l 得到的 apk 版本一致
```

### 档 2：手上只有 202602260 时，同步下调 PMS 记录

必须**同时**改记录与清缓存，否则永远不合：

```bash
su
stop            # 或 killall system_server（框架需停止，否则 packages.xml 会被回写）
# 编辑 /data/system/packages.xml：com.android.systemui 的 version="102602260" → "202602260"
sed -i 's/\(<package name="com.android.systemui"[^>]*version=\)"102602260"/\1"202602260"/' /data/system/packages.xml
rm -rf /data/system/package_cache/*/MiuiSystemUI*
rm -f  /data/dalvik-cache/arm64/system_ext@priv-app@MiuiSystemUI@MiuiSystemUI.apk@classes.*
start
```

风险提示：
- `stop` 之后再 `start` 期间界面全无，操作窗口短，命令必须一次跑完（建议写成脚本在 adb/root shell 里执行）。
- 重扫时 PMS 可能覆盖回旧值，成功率不保证。
- 修改 `packages.xml` 属于对 PMS 的侵入式操作，**可能触发救援/校验机制**，务必先备份：`cp -a /data/system/packages.xml /data/local/tmp/packages.xml.bak`。

### 档 3：OTA / 恢复出厂

OTA 包版本必然 ≥ 102602260，会同时刷正 `/system_ext` 与 PMS 记录，是最彻底的。代价是数据。

## 12.7 反直觉推论：重新启用模块反而能解决僵局

既然 **PMS 记录 = 102602260**，而 **模块 overlay 里的改装版 = 102602260**，二者天然一致：

```
PMS 记录：102602260
overlay ：102602260（systemui_mount）
→ 状态一致，PMS 无降级判定
```

所以当前僵局的**最快临时解法**不是去找原版 apk，而是：

```bash
su
rm -f /data/adb/modules/systemui_mount/disable
reboot
```

**前提**：改装版 apk 内容本身没有引入崩溃。若改装内容有 bug，则从「版本矛盾黑屏」变成「改装 bug 黑屏」，两者表现相似但根因不同——需先用 12.3 的 `kmsg.txt` 确认 10-18 那次启动超时的具体报错。

这也泄露了一个重要事实：**当前设备处于「磁盘 202602260 / PMS 102602260」的矛盾态，而「磁盘与 PMS 都回到 102602260」比「两者都回到出厂值」更容易达成。**

## 12.8 给模块与救援脚本的硬规则

1. **改装系统应用，versionCode 只能升不能降。** 抬高了就必须有配套的「回退到同等或更高版本」方案，否则等价于单向门。
2. **绝不要用「降低 versionCode 的 apk」做救砖源。** PMS 的降级拒绝是权限、SELinux 之外的第三道闸门，绕过前两道没有意义。
3. **救砖脚本必须先读三方版本再动作**：源 apk versionCode、目标 apk versionCode、PMS 记录 versionCode。任一比较不通过就拒绝执行并打印原因。
4. **救砖脚本必须校验生效**：覆盖后重新读 `dumpsys package | grep versionCode`，确认记录已变化；未变化说明被拒绝，此时应回滚而不是宣告成功。
5. **不要假设系统救援会兜底。** 本机实测：RescueParty 等级恒 0、`RescuePartyLog` 空、`disable_autorestart` 未写。系统把降级矛盾当作合法状态，自愈路径全部绕过。
6. **区分「overlay 层修复」与「物理层修复」。** 两者叠加时优先级由 mount 顺序决定，混用会产生难以推理的状态。要么只走 overlay（模块启用/禁用），要么只走物理层（直接替换分区文件），不要混。

## 12.9 一句话结论（二次修正版）

> 第 11 章的「无限热重启软砖」是**代码推导的预期**，本机实测未发生。
> 第 12 章初版的「物理分区被塞入低版本 apk」也已由本轮实测证伪（`PROTECT_COUNT=0`、磁盘 apk `mtime=2009-01-01`）。
>
> **修正后的结论**：真正发生的是 ——
> **模块 overlay 生效 → PMS 按 overlay 内容记录 102602260 → 模块被禁用 → overlay 消失、PMS 记录不刷新 → 留下「记录高版本 / 磁盘低版本」的陈旧元数据。**
>
> 这一不一致**既不会导致黑屏，也不会阻止 SystemUI 启动**（实测 SystemUI 在 `disable` 状态下正常运行）。
> 它的真实危害是**留下一个随时可能被触发的隐患**：一旦发生 OTA、重新 scan、`pm install -r` 等会重新读取 apk 的操作，
> PMS 就会读到 202602260，判定为降级并静默拒绝，届时才会真正进入「包状态自相矛盾」。
>
> 整个过程中，`RescuePartyXM` / `PackageWatchdogImpl` / `RescuePartyPlusHelper` **一次都没有介入**，
> 因为它们只认崩溃次数与 boot failure 计数，而 overlay 失效既不产生 crash、也不产生 ANR。
> 系统的所有自愈路径共享同一个盲区：**「overlay 静默失效」在它们眼中是完全正常的状态**。
>
> 因此结论是：**这类「覆盖系统应用」的模块，其故障模式落在系统急救机制的判据真空区——
> 模块自己的救砖脚本救不了（流程前置条件苛刻，见第 13 章），系统急救机制也感知不到。
> 真正的防护只能在「安装前校验」与「卸载前回滚」两端做，而不是靠事后救砖。**

# 13. 救砖模块 vs 系统急救机制 —— 源码级审计

> 本章基于对 `systemui_mount` 模块**全量源码审计**（`action.sh` / `service.sh` / `config/log.sh` / `webroot/webctl.sh` / `webroot/safety.sh` / `webroot/check.sh` / `webroot/index.html` / `webroot/assets/app.js` / `update.md`）与实机状态核查得出。
> 这是回答「它和系统自带急救机制有什么冲突」的正面答案。

## 13.1 模块身份与版本错位

| 项 | 设备实际（`/data/adb/modules/systemui_mount`） | 分发包（`模块样本.zip`） |
|---|---|---|
| `id` | `systemui_mount` | 同 |
| `name` | 日志版挂载界面 | 同 |
| `version` | **2.1** | **1.5.1** |
| `versionCode` | **10** | **11** |
| 作者 | XKspeed | 同 |
| `action.sh` | **3,933 B**（简陋版） | **517 行 / ~13 KB**（四层检测版） |
| `system_ext` 布局 | **符号链接** `system_ext -> ./system/system_ext` | `system_ext/` 真实目录（+ 遗留空目录 `system/system_ext/`） |
| 救砖成功次数 | **`PROTECT_COUNT=0`** | — |

**签名含义**：设备上装的是**旧版 2.1**，而分发包是 1.5.1。1.5.0 才引入 WebUI、`safety.sh`、`check.sh`、黑屏卡死检测（1.3.0）等。
→ 设备上的 2.1 只有最原始的「等 PID 变化 + 音量键 + cp」救砖，**没有**崩溃自动救砖、没有日志疯长/StackOverflow 检测、没有 `safety.sh` 保底、没有 RescueParty 开关。

**布局差异是真实隐患**：`system_ext -> ./system/system_ext` 是旧版兼容技巧。
Magisk 官方模块规范是 `$MODPATH/system_ext/`（顶层真实目录）。
在 KernelSU + metamodule（本机为 `mountify`）环境下，**顶层符号链接是否被 magic mount 正确识别没有保证**。
一旦不被识别 → overlay 静默不生效 → 无任何报错 → 用户以为「模块已启用但界面没变」，而系统用原厂 apk 正常工作，**连「该救」的信号都不会产生**。

## 13.2 分发包 1.5.1 的四层救砖设计

`action.sh` 已从「单一崩溃计数」扩展为四条独立的出口：

| 出口 | 判据 | 阈值（可配） | 解决的问题 |
|---|---|---|---|
| ① 崩溃计数 | `logcat -b crash` 匹配 `FATAL EXCEPTION` + `Process: com.android.systemui` 等 6 种模式 | `FATAL_THRESHOLD=3` | 常规崩溃循环 |
| ② 日志疯长 | 单轮日志增长 > `LOG_FLOOD_BYTES` | 2 MB | **进程活着但界面卡死** |
| ③ 堆栈溢出 | 堆栈行 > 5000 且占比 > 80% | — | `StackOverflowError`（如 `SimCarrierView` 递归，单次 7 万行/16MB，30 秒只崩 2 次，永远够不到阈值 3） |
| ④ 音量键 | `getevent` 读 `/dev/input/event*` | 手动 | 兜底 |

另有 `webroot/safety.sh` 的 **arm 30 秒保底**：到点无条件恢复界面，不依赖 `action.sh`、不依赖音量键。
以及 `LOG_MAX_BYTES=50MB` 防止写爆存储。

**这套设计本身是成熟的**——它承认并绕开了好几个真实坑（`update.md` 里都有记录）：

- **音量键能力位图 ≠ 实际事件**：`uinput-goodix` 声明了 `KEY_VOLUMEUP/DOWN` 却一次事件都不产生；内核位图「高位字在前、每字左侧不补零」，`8000000000000 0` 实际是 bit115 而非 bit12。
  → 改为按 `bit115`(音量+) / `bit114`(音量−) 识别 + 四步实测（扫描声明者 → 实测哪个真收到 → 用户选 → 最终校验）。
- **能力位图解析兼容 32/64 位内核**：8 或 16 个十六进制字符都试。
- **`getevent` 只接受一个 device 参数**（传多个会打印 usage 退出）→ 每个设备单开进程、单开输出文件，避免事件串台。
- **`logcat` / `getevent` 加 `setsid`**，避免父进程退出时被进程组清理。
- **`ksu.exec` 是同步阻塞的**，一次调用无法中途更新 UI → WebUI 校验拆成 `env → up → down → save` 四次串行调用。

## 13.3 为什么 `PROTECT_COUNT=0` —— 救砖一次都没跑成

设备版 2.1 的 `action.sh` 流程（源码逐句）：

```
OLD=$(pidof com.android.systemui)
[ -z "$OLD" ] && { while [ -z "$OLD" ]; do sleep 1; OLD=$(pidof ...); done; }   # ← ① 无限死等
W=0
while [ "$W" -lt "$KEY_TIMEOUT" ]; do                                          # ← ② 等 PID 变化
    NEW=$(pidof com.android.systemui)
    [ "$NEW" != "$OLD" ] && [ -n "$NEW" ] && break
    sleep 1; W=$((W+1))
done
[ "$W" -ge "$KEY_TIMEOUT" ] && exit 0                                          # ← ③ 没变化就静默退出
key=$(timeout ${KEY_TIMEOUT} getevent -qlc 1 | grep ...)                        # ← ④ 再等音量键
[ -z "$key" ] && exit 0                                                        # ← ⑤ 超时退出
KEY_VOLUMEUP) T=1 ;;                                                           # ← ⑥ 必须按音量+
[ ${T} -eq 0 ] && exit 0
cp -f "${APK}" "${AIM_APK}"                                                    # ← ⑦ 才真正救砖
```

**成就一次救砖需要连续闯过 7 关，任一步失败就静默退出、不留下任何提示。**

三个致命的前置条件：

1. **必须先替换界面**（②③）：`action.sh` 等的是 SystemUI **PID 发生变化**，`KEY_TIMEOUT=30` 秒。
   如果用户在 WebUI 里点了「开始」，然后什么都不做 → 30 秒后静默退出 → 什么都没干。
   这对应 `update.md` 的说明：「等待用户替换界面（PID 变化）：保留 KEY_TIMEOUT 超时，防止误启动后一直挂着」。
2. **必须在 30 秒内按音量+**（④⑤⑥）：替换完成后还要再按一次音量+，按音量− 就直接取消。
3. **① 是真正的死局**：若 SystemUI 起不来（`pidof` 为空），脚本进入 `while [ -z "$OLD" ]` **无限循环**，
   既不超时、也不报错、也不执行救砖——**恰恰在最需要救砖的黑屏场景下，脚本永久卡死**。

**这就是 `PROTECT_COUNT=0` 的根本原因**：流程要求「先手动启动守护 → 再主动重启 SystemUI → 再 30 秒内按音量+」，
前置动作全部依赖**用户能看到界面并完成精细操作**，而黑屏场景下这三件事一件也做不到。

**更深一层的悖论**：这个救砖设计的前提是「SystemUI 崩溃但系统还能操作」。
它完全无法处理「overlay 静默失效 / 版本降级 / PMS 状态矛盾」这类**不产生崩溃**的故障——
因为它的所有判据（①②③）都是"崩溃"或"卡死"的间接信号。

## 13.4 「屏蔽系统 RescueParty」开关的真实实现（关键发现）

这是 `update.md` v1.5.0 声明的新功能，UI 在设置页最顶部（`webroot/index.html:121-145`，`id="rescue-toggle"`），
风险提示文案：

> 该设置是持久型设置 只能通过这里开关
> 开启后 系统的救砖机制失效 造成的后果自负

**实现代码**（`webroot/webctl.sh:157-184`，`app.js:739-741` 绑定 `change` 事件）：

```sh
rescue)
    ACTION="${2:-get}"
    case "$ACTION" in
        get)
            V=$(dumpsys activity settings | grep -oE 'process_crash_count_limit=[0-9]+' | cut -d= -f2 | head -1)
            echo "limit=${V:-unknown}"
            if [ "${V:-0}" -gt 100 ] 2>/dev/null; then echo "state=off"; else echo "state=on"; fi
            ;;
        off)
            settings put global activity_manager_constants \
                "process_crash_count_limit=999999,min_crash_interval=120000,process_crash_count_reset_interval=43200000"
            echo "OK 已屏蔽系统救援"
            ;;
        on)
            settings put global activity_manager_constants \
                "process_crash_count_limit=12,min_crash_interval=120000,process_crash_count_reset_interval=43200000"
            echo "OK 已恢复系统救援"
            ;;
    esac
```

**原理**：`process_crash_count_limit` 对应 AOSP `ActivityManagerConstants.KEY_PROCESS_CRASH_COUNT_LIMIT`（默认 12）。
AMS 在 `handleAppCrashLocked` 里累加 `mProcessCrashCount`，超过上限才进入救援分支。
把上限改成 **999999** → 计数永远达不到 → `RescueParty` 的 `noteAppCrash` 永不被调用 → **系统救援彻底失效**。

**这个手段本身是有效的**（比 hook 简单、无需 Xposed），但有四个严重问题：

1. **整串覆盖风险**：`settings put global activity_manager_constants` 写入的是一个逗号分隔的 `key=value` 串，
   **会整体替换原有值**。若厂商（小米）在该 key 里预置了其它参数（如 `service_crash_restart_duration`、`max_service_crashes`、`max_cached_processes`），
   会被**一并抹掉**，改变其它 AMS 行为，且 `on` 恢复时只写回 3 个参数，**原值永久丢失**。
2. **全局生效**：影响**所有应用**的崩溃兜底，不只 SystemUI。任何 App 进入永久崩溃循环都不会被系统回收/救援。
3. **对本模块要防的真实故障完全无效**：overlay 静默失效、符号链接不被识别、versionCode 降级——这些**不产生 crash 计数**，
   `process_crash_count_limit` 是大是小毫无区别。这个开关给用户「我已关掉系统救援，我自己能救」的**错觉**。
4. **反向恶化**：若将来真的出现 crash 循环（例如用户换了签名不符的 apk → 每次启动必崩），
   系统本会在第 12 次崩溃时清数据 + warm reboot（粗暴但能出图），现在被这个开关废掉 →
   **从「清数据但能开机」退化为「永久黑屏」**。

> **一句话**：这个开关是**唯一真正接入系统层**的功能，却恰好作用在「本模块故障模式覆盖不到」的那条路径上，
> 同时拆掉了系统唯一会强制出图的兜底手段。

## 13.5 六处真实冲突

### 冲突 ① 判据真空区 —— 两套体系谁都不认这类故障

| | 模块救砖的判据 | 系统急救的判据 |
|---|---|---|
| 信号源 | `logcat -b crash` 缓冲匹配（崩溃 / 日志疯长 / StackOverflow） | `PackageWatchdog` 崩溃计数、`BootFailure` 计数、`Watchdog` |
| 触发阈值 | 3 次崩溃 / 2MB 单轮增长 / 5000 行堆栈 | `process_crash_count_limit=12` |
| 覆盖故障 | 崩溃循环、界面卡死 | 崩溃循环、开机失败 |

**overlay 静默失效 / 版本降级 / 符号链接不被识别** → 既不产生 crash，也不产生 ANR，也不产生 boot failure 计数。
→ 模块检测不到，系统也检测不到。
→ **黑屏卡死落进两者之间的真空区，谁都不救。**

**实测证据**：`getprop` 中救援相关仅 `sys.mqs.recorder.rescueparty.finish=true`；
`/mnt/rescue/mqsas/RescuePartyLog` 为空；`sys.rescueparty.systemui.level=0`；
`/mnt/rescue/mqsas/UnhealthyBootLog` 里只有 `bm_hyperboot_timeout_901005303_popsicle_OS4.0.0.23.XPBCNXM_5953118.zip`（HyperBoot 超时取证包）和 `kmsg.txt`，
**没有任何 RescueParty 动作记录**。

### 冲突 ② 修复对象错位 —— 一个修 overlay，一个修 /data

- **模块救砖**：`cp -f "$APK" "$AIM_APK"`，只改 `$MODDIR/system_ext/priv-app/MiuiSystemUI/MiuiSystemUI.apk`（overlay 源）。
- **系统急救**：`clearAppCacheAndData()` → `deleteApplicationCacheFiles` + `clearApplicationUserData`；
  卸载 `miui.systemui.plugin` / `com.miui.aod`；`resetFont` / `resetTheme`；warm reboot。
  经全量 grep 确认：**救援动作里没有任何"安装/重装/还原 apk"的代码路径**
  （`reinstall[A-Za-z_]*` 仅 2 处命中，属 `BackgroundPreinstalloptService`，与救援无关；
  `com/android/server/crashrecovery` 子包内 `install` 零命中）。

→ **模块治 /data/adb 的 overlay 文件，系统治 /data 下的用户数据。谁也治不了对方的病。**
→ 更糟：系统救援的 `clearAppCacheAndData` 对本故障**纯属误伤**（清掉用户数据却对 overlay 无效）。

### 冲突 ③ 时序错位 —— 模块 3 次就动手，系统 12 次才兜底

- 模块 `FATAL_THRESHOLD=3`（且 `update.md` 明确提醒「替换 APK 本身可能引发一次崩溃，阈值建议 ≥3」）。
- 系统 `process_crash_count_limit=12`。

→ **模块先动手（第 3 次崩溃就 cp 换文件），系统后动手（第 12 次才清数据热重启）。**
→ **若模块的「救砖文件」本身是坏的**（签名不符 / versionCode 更低 / 缺依赖的改装版）：
  模块换上去 → 继续崩 → 崩到第 12 次 → **系统清数据 + 热重启** → 用户数据没了，overlay 还是坏的 → **双重损失**。
→ **这就是「模块的救砖失败会把问题升级为数据丢失」的机制**：不是两套体系打架，而是**模块的失败递交给系统后，系统的动作更粗暴且不可逆**。

### 冲突 ④ 屏蔽开关方向反了（详见 13.4）

`process_crash_count_limit=999999`：
- 对**本模块实际会遇到的故障**（overlay 失效、降级）→ 无效；
- 对**系统唯一能强制出图的路径** → 拆除。

### 冲突 ⑤ 救砖动作零校验 —— 全模块无 versionCode / 包名 / 签名检查

**全模块 grep 结论**（`versionCode|version_code|aapt|badging|dumpsys package`）：
**仅 1 处命中，是 `module.prop` 自己的 `versionCode=11`。**
`webctl.sh` 的 `prepare`（用户选「救砖文件」时）只校验三点：

```sh
[ ! -f "$SRC" ]           && FAIL 文件不存在
case "$SRC" in *.apk|*.APK) ;; *) FAIL 不是 APK ;; esac
unzip -l "$SRC" >/dev/null 2>&1 || FAIL APK 已损坏
```

**不校验包名、不校验 versionCode、不校验签名、不校验与 PMS 记录是否兼容。**

→ 用户可以选中**任何** apk 作为「救砖文件」（甚至别的应用的 apk），模块照单全收。
→ 救砖时 `cp` 上去，重启后 SystemUI 起不来（签名不符必崩 / 包名不符直接失败）。
→ **同一问题在 `action.sh` 侧同样存在**：救砖段落只检查 `[ ! -f "${APK}" ]`，然后 `cp -f`。

> 这与分发包 `update.md` 里那句自认高度一致：
> 「**WebUI 自动测试功能暂时下线 —— 原因：脚本写入 APK 无法触发 SystemUI 重新加载，MT 管理器写入可以**」。
> 即作者本人已经放弃了「脚本能安全替换 SystemUI」这一假设。

### 冲突 ⑥ `safety.sh` 与 `action.sh` 的恢复目标可能互相覆盖

`update.md` 声明 `safety.sh` 是「与救砖逻辑完全独立」「到点无条件恢复界面，不依赖 action.sh 和音量键」，写入方式「大小相同用 dd，不同用 cp」。

但两者写的是**同一个文件** `$MODDIR/system_ext/priv-app/MiuiSystemUI/MiuiSystemUI.apk`。
若 `action.sh` 先 cp 了文件 A，`safety.sh` 的 30 秒到点又 cp/`dd` 了文件 B（或反过来），
**最终生效的是后写者**，且双方都不检查当前文件内容、都不做 versionCode 比较。
→ 存在「救砖与保底互相覆盖」的竞态，结果是不可预测的。

## 13.6 硬规则（给模块作者 / 自己写模块时）

1. **覆盖系统应用的模块，救砖不能靠事后脚本，必须靠「安装前校验 + 卸载前回滚」**
   - 安装前：读 `dumpsys package <pkg> | grep versionCode`，与候选 apk 的 `versionCode` + 包名 + 签名（`apksigner verify` / `pm dump`）比对，不匹配**直接拒绝**。
   - 卸载/禁用前：检测 PMS 记录是否因 overlay 而被抬高了 versionCode，若是则提示「禁用后记录会陈旧」或自动把原厂 apk 恢复进 overlay 再禁用。
2. **overlay 一律用 `$MODPATH/system_ext/`（顶层真实目录），禁止 `system_ext -> ./system/system_ext` 符号链接**。
   旧版兼容技巧在 KernelSU + metamodule 下无保证，且失效时**静默无报错**。
3. **救砖判据必须包含「overlay 是否真的生效」**，而不是只监听崩溃：
   - 校验 `mount | grep MiuiSystemUI` 是否有 overlay；
   - 校验 overlay 目标文件与 `dumpsys package` 的 versionCode 是否一致；
   - overlay 未生效应视为**最高优先级故障**（因为它不会产生任何崩溃信号）。
4. **救砖脚本绝不能有「无限死等」分支**。`while [ -z "$OLD" ]; do sleep 1; done` 在
   「SystemUI 起不来」这一最需要救砖的场景下永久卡死，必须改为有限重试 + 超时后走保底路径。
5. **不要用 `settings put global activity_manager_constants` 屏蔽 RescueParty**：
   它会整串覆盖厂商预置值、全局影响所有应用、且对本类故障无效。
   若确需屏蔽，应只针对 SystemUI 单包（`PackageWatchdog` 层的 `forget` / `disable` 接口），并**先备份原值**。
6. **`LOG_MODE=0`（静默）作为出厂默认是危险的**：分发包 `config/settings.conf` 默认 `LOG_MODE=0`，
   意味着「开箱即用状态下所有自救全部关闭，只有 overlay 替换生效」。出事时用户没有任何日志、没有任何自救。
   建议默认 `LOG_MODE=1`（仅记录日志，不自动动手）——**先有证据，再谈修复**。

## 13.7 对本次故障的最终判定

| 问题 | 判定 |
|---|---|
| 系统急救机制被模块屏蔽了吗？ | **没有**。模块的 RescueParty 屏蔽只是 `settings` 开关，且从未在本机开启；`sys.rescueparty.systemui.level=0`，救援链从未触发。 |
| 系统急救为什么没救回来？ | **它从未介入**（详见第 12 章 + 13.5 冲突①）。它只认崩溃计数与 boot failure，而 overlay 失效不产生这些信号。 |
| 模块的救砖机制为什么没救回来？ | **它一次都没跑成**（`PROTECT_COUNT=0`），因为流程要求「手动启动 → 主动重启 SystemUI → 30 秒内按音量+」，黑屏场景下无法完成；且遇到 `pidof` 为空时永久死等（13.3）。 |
| 那设备现在为什么是好的？ | 因为磁盘 apk（202602260）本身是**完好的原厂版本**，`disable` 状态下系统直接用它运行，`codePath` 未变故 PMS 不重新扫描，陈旧元数据不影响启动。实测 SystemUI 正常运行（`pidof` 有值）。 |
| 遗留隐患是什么？ | PMS 记录 `102602260` 与磁盘 `202602260` 的**陈旧不一致**会在下次 OTA / 重新 scan / `pm install -r` 时被触发，届时才真正进入「降级被静默拒绝」的僵局。 |
| 怎么根治？ | 让「PMS 记录」与「实际加载的 apk」重新对齐：① 恢复模块 overlay（删 `disable`）让两者天然一致，但需先确认 `system_ext` 符号链接在 mountify 下真的生效；② 或把物理分区 apk 换成 102602260 版（改只读分区，OTA 会覆盖）。**优先 ①**，并用 `mount \| grep MiuiSystemUI` 与 `dumpsys package` 双向验证。 |
