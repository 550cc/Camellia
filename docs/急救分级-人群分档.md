# 分级急救机制设计 v3（DE 是唯一战场）

> 状态：设计稿，未编码
> v3 修正 v2 的致命错误：v2 假设「DE 保命 → 解锁后用 pm 校正」。**但 SystemUI 崩了，锁屏就画不出来，用户无法解锁，CE 永不解密，`pm` 永不可用**。那条路不存在。

---

## 0. 硬前提（决定了整个架构）

```
SystemUI 崩 → 黑屏 / 锁屏不可交互
          → 用户输不进密码 → 无法解锁
          → CE 不解密 → /data/data 不可访问
          → system_server 未到 boot_completed → pm 不可用
          → 重启也无效（坏包还在，开机继续崩）
```

**结论：故障现场永远停在 DE。已解锁只是"还没坏的时候"的状态，不是急救现场。**
所以急救必须**全部在 DE 阶段闭环**，`pm clear` / `pm install` 不能作为主手段。

---

## 1. 故障分两级严重度

| | 症状 | 能否救 |
|---|---|---|
| **S1** | system_server 起来了，SystemUI 反复崩（黑屏、无锁屏） | ✅ camd 可在 DE 修 |
| **S2** | system_server 也崩（PMS 解析坏插件时崩）→ 无限 bootloop，ADB 都连不上 | ⚠️ 必须在 system_server 启动**之前**预防性禁用 |

S2 是真正的砖，只有 init 阶段能拦。

---

## 2. 三层防线

| 防线 | 时机 | 手段 | 目标 |
|---|---|---|---|
| **① 预防** | 安装时 | 安装闸门 + 健康快照 | 保证总有可回退的 Good |
| **② DE 急救** | SystemUI 崩循环 | 禁用组件 / 覆盖本体 + 杀 system_server | 让 SystemUI 起来 → 用户能解锁 |
| **③ 开机兜底** | 连续 boot 失败，init 阶段 | 预防性禁用所有第三方组件 | 保开机（S2 唯一出路） |

---

## 3. 崩溃循环检测（DE 阶段的核心判据）

DE 阶段没有 `pm`，也不能靠 `boot_completed`。用：

```
窗口 W = 120s，采样 pid_of_pkg("com.android.systemui")
  pid 变化次数 ≥ 3 次   → 判定 "sysui_crash_loop"
  或 开机 > de_wait_sec(90s) 仍无 pid → 判定 "sysui_dead"
```

不用 logcat（DE 阶段 logd 可能有，但不可靠），只看 pid 变化，最稳。

---

## 4. 自动安全模式（最关键的一条，尤其对小白）

> 小白没有任何操作能力。他唯一能"做"的事就是等，或者重启（重启无效）。

```
触发：sysui_crash_loop 或 连续 boot 失败 ≥ 2 次
动作：
  1. 扫描所有非系统 plugin / overlay（/data/app 下带 SYSTEMUI_PLUGIN/OVERLAY 特征的包）
  2. 逐个 mv 成 .off（可回滚，不删）
  3. sync
  4. killall system_server
效果：SystemUI 用纯系统组件起来 → 锁屏恢复 → 用户能解锁
```

- **对小白**：这是唯一零操作的自愈路径。
- **对玩机佬**：解锁后状态卡显示「已进安全模式，禁用了 X/Y/Z」，可一键逐个恢复、定位是哪个包的问题——这反而是他想要的诊断信息。

**为什么"禁用"优于"清数据"**：DE 阶段清不了 CE；而禁用后插件根本不加载，它的坏数据自然不参与，效果等价且可逆。

---

## 5. 目标类型：决定能不能"禁用"

| 目标 | fallback | DE 阶段手段 |
|---|---|---|
| `miui.systemui.plugin` 等组件 | 有（SystemUI 退化但能起） | `mv .off` → 立刻可用 ✅ |
| `com.android.systemui` 本体 | **无** | 不能删/改名（PMS 标 missing，可能丢包）→ 只能 `cp 快照覆盖 base.apk` + 删 oat + 杀 system_server |

## 7. 各级 × 现场（DE 必须全能，B 降级为收尾）

| 级 | DE 未解锁（唯一主战场） | 已解锁（若真的到了） |
|---|---|---|
| L0 | 读 packages.xml、pid 采样 | dumpsys |
| L1 | 组件 `mv .off`；本体禁止 | `pm uninstall-system-updates` |
| L2 | `cp 快照 → base.apk` + 删 oat + sync | `pm install -r -d` |
| L3 | 只清 `/data/user_de/0/<pkg>`；CE 记 `pending_clear` | `pm clear`（补执行） |
| L4 | `killall system_server` | 同左 |
| L5 | 熔断 / 进安全模式 | 同左 |

**L3 在 DE 几乎用不上**，因为"禁用组件"已经等效解决；保留它只为处理本体类的 DE 数据。

## 8. 物理按键急救（可选，小白的第二条命）

DE 阶段无法点屏幕，但可以读 `/dev/input/event*`：

```
长按 音量下 + 电源 15s → 强制进入自动安全模式
```

- 小白唯一可执行的手动入口（不需要看屏幕）
- 玩机佬也方便：不用等自动检测
- 代价：需要 input 设备权限（camd 是 root，可读），且要处理不同机型 event 映射

---

## 9. 安全边界（写死）

1. L2 无快照不执行；覆盖前校验 sha256 + 先 bak 现状
2. `com.android.systemui` 本体禁止删/改名，只能原地覆盖
3. 安全模式只 `mv .off`，**永不删除**，保证可逆
4. 单 boot：L2 ≤ 2、L4 ≤ 1、进安全模式 ≤ 1
5. 连续 3 次 boot 都失败 → L5 永久熔断，只保开机，不再尝试修复
6. 所有动作写 `rlog`，且**不把 stderr 指向 `/data/adb` 下的文件**（会污染子进程 fd，已踩过的坑）
