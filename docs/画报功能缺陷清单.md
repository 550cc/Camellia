# 小米画报（com.mfashiongallery.emag）Hook 缺陷清单与修复记录

> 涉及文件：`src/com/hyper/Camellia/Fg.java`
> 逆向基准：设备实际安装版本 25200037-CAROUSEL（versionCode 2025200037，4 dex，19003 类）

## 0. 设计前提（两条互斥路线）

| 路线 | `localPhoto` | 写哪张表 | 画报模式 |
|---|---|---|---|
| 自选壁纸注入 | `false` | `lks_wp`（`bizids='cw'`, `type='l_pic'`） | `custom_wallpaper` |
| 右滑轮播接管 | `true` | `feedcache`（`req_tag='left_lks'`） | `auto_recommand_paper` |

两条路线**必须互斥**。旧实现让 ①②③④ 段无条件执行，等于同时走两条路线，
这是「一团乱麻」的总根源。

## 1. 逆向校准到的关键事实

1. 画报「模式」只存在于 SharedPreferences `setting` 的 `sst_mode` 键，
   判定入口 `ssetting.SSettingUtils.isSstMode(String)`；
   原生「锁屏壁纸轮播 / 推荐壁纸」的合法值是 **`auto_recommand_paper`**。
2. 数据库模式记录在 `setting` 表 `mode_type`；`SettingManager.saveToDb` 写
   `attr=2` 表示**本地设置**，而 `cleanOnlineSetting()` 按 `attr` 删除在线下发项。
   故 `attr=1` 的行会被画报自己清掉。
3. `lks_wp` 表 authority 取自 `db.MiFGDBDef.CONTENT_AUTHORITY`（= `com.mfashiongallery.emag.main`）。
4. `feedcache` 的 `WallpaperHealth` 清理条件是
   `req_tag=? AND show_t>0 AND show_t<?` —— 模块写 `show_t=0`（未展示），
   不会被误清；但**一旦写入非 0 show_t 就会被当过期数据删掉**。
5. `lks_wp` 与 `feedcache` 是两个不同 authority / 表，右滑完全不读 `lks_wp`。

## 2. 缺陷清单

### 缺陷 1（致命）右滑接管时仍然写 lks_wp
`sync()` 的 ①删除 / ③插入 / ④b去重 段无条件执行。`localPhoto=true` 时
本地图仍被塞进画报原生锁屏推荐池，而模式又不是 `custom_wallpaper`，
于是锁屏固定一张 / 灰块 / 不轮播与右滑接管同时坏掉。

**修复**：引入单一真源 `boolean writeLks = !cfg.localPhoto && uri != null`，
①②③④ 全部纳入该条件。

### 缺陷 2（致命）模式常量取值非法
`MODE_LKS = "lockscreen"`。`"lockscreen"` 只是画报埋点里的页面 scope 名，
不是模式值。写进去后 `isSstMode` 两个分支都不成立，画报落进未知模式。

**修复**：新增 `MODE_NATIVE = "auto_recommand_paper"`，`MODE_LKS` 作为其别名保留。

### 缺陷 3（严重）setting 表写入 attr=1 被画报清理
模式写入时 `attr="1"`，随后 `cleanOnlineSetting()` 会删掉该行，模式写入
「时灵时不灵」。

**修复**：新增常量 `SETTING_ATTR_LOCAL = 2`；insert 与 update 两处同时写
`attr=2`（update 语句补了 `attr=?`，可顺带修正历史脏行）。

### 缺陷 4（严重）revokeLks 是死代码
`revokeLks()` 只有定义、全项目无调用。接管右滑时历史注入行永久留在
`lks_wp`，模式却被切走 —— 既不是纯原生推荐，也不是自选壁纸。

**修复**：新增 `revokeLksThrottled(ctx, uri)`（进程内首次立即执行，
之后 60s 一次），在 `writeLks == false` 分支调用。

### 缺陷 5（致命）wipedNow 在接管路线恒为 true
`privLooksWiped()` 检查的是「画报私有缩略图副本目录」文件数，而**接管右滑
路线根本不会生成私有副本**，因此恒返回 `true`。旧代码
`if (cfg.localPhoto && !wipedNow) restoreLksMode(ctx);` 于是几乎永不执行，
画报永久停在 `custom_wallpaper`。

**修复**：`wipedNow` 只在注入路线计算
（`!cfg.localPhoto && privLooksWiped(...)`），接管路线改为无条件撤销 + 切模式。

### 缺陷 6（性能/写放大）purgeCurated 每轮全表扫
`sync()` 每 800ms 一轮，每轮都 query 全部 `req_tag='morning_detail'` 的
`raw_d` 并逐条 delete。

**修复**：白名单 + 时间双键节流（同一份白名单 60s 内只执行一次）。

### 缺陷 7（构建一致性）两套构建入口版本脱节
`build.sh` 里 `VERSION=2.15.0 / VCODE=60`，而 `build.gradle` 为
`2.15.6 / 66`；Gradle 侧只同步 `module.prop`，不回写 `build.sh`。

**修复**：`build.sh` 版本同步为 `2.15.6 / 66`。

## 3. 未修改但已知的风险点

1. `syncLeftLks` 在缩略图全部就绪时**整批删除 `req_tag='left_lks'` 再重插**，
   行无法按路径区分。若画报在同窗口读取，可能短暂少图。
2. `feedcache.cache_o` 写的是当前时间，若画报按 `cache_o` 做 TTL 判过期，
   模块插入行可能被整体刷新掉（未在 APK 中确证存在该 TTL）。
3. `sst_mode` 写 SharedPreferences 用 `apply()`，画报若在其它进程持有该
   sp 实例，跨进程可见性依赖框架自身处理。
4. 遗留死代码：`hookReplaceUri`、`pickLocalPhoto`、`isLocalPick`、`argAt`。
5. `build.sh` 不编译 Kotlin（4 个 `.kt`），正式产物必须用 Gradle 构建。

## 4. 构建

```bash
/opt/gradle-9.8.0/bin/gradle assembleDebug --no-daemon \
  -Dorg.gradle.vfs.watch=false \
  -Djava.io.tmpdir=$PWD/.gradle-tmp
# 产物：build/outputs/apk/debug/Camellia-debug.apk
```

注意：系统自带 `gradle` 为 8.5，不满足项目 AGP 要求（最低 9.6）。
